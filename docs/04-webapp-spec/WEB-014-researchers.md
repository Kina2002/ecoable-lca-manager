# WEB-014 가상 담당자·연구원 등록·선택·담당 프로젝트

## 1. 목적과 합의

사용자는 다른 샘플에도 가상 고객 담당자를 넣고 우리 측 연구원 탭을 요청했다. ‘이름과 맡은 프로젝트 조회’와 ‘연구원 등록 후 프로젝트에서 선택’ **둘 다** 원한다고 확인했다.

담당 연구원을 프로젝트마다 이름으로만 적으면 동명이인을 구별하거나 여러 프로젝트를 모아 보기 어렵다. 연구원 명단과 프로젝트의 담당 연결을 분리해 ID로 연결한다. F-01의 담당자 연결 일부와 사용자 추가 화면이며 직원 인사·로그인·권한 기능은 아니다.

## 2. 화면

### 담당 연구원 탭

- 사이드 메뉴에 **담당 연구원**을 추가한다.
- 이름(필수, 앞뒤 공백 정리, 1~100자)으로 가상 연구원을 등록한다. 모두 가상 표시를 한다.
- 기본 3명과 직접 등록한 연구원을 함께 보여준다. 고유 번호는 `RSR-001` 형식이며 첫 직접 등록은 `RSR-004`다.
- 동명이인도 별도 ID·번호로 등록할 수 있다. 목록·프로젝트 선택에서 이름과 번호를 함께 표시한다.
- 각 연구원의 담당 프로젝트 수와 회사·제품·현재 단계·프로젝트 번호를 보여준다. 완료 단계도 포함하며 인원별 실적 평가나 업무량의 정밀 지표가 아니다.
- 프로젝트 번호를 누르면 상세를 연다. 이후 목록으로 돌아가면 프로젝트 전체 목록을 보여준다.
- 연구원 명단으로 연결되지 않은 기존 이름 기록은 **연구원 연결 확인**, 아무 이름도 없는 프로젝트는 **담당 연구원 미정**으로 따로 표시한다. 같은 이름만으로 자동 연결하지 않는다.

### 프로젝트 상세

- 계약 단계 ‘담당자와 착수 준비’의 고객 담당자는 기존처럼 이름을 입력한다.
- 담당 연구원은 등록된 목록에서 **이름·고유 번호**를 보고 선택한다.
- 담당자 저장 시 연구원 ID를 최신 명단에서 조회해 이름을 함께 보관한다. 임의로 보낸 이름을 신뢰해 다른 사람으로 기록하지 않는다.
- 기존 범위 내용·합의 상태·단계는 유지한다. 두 담당자가 저장되면 기존 별도 범위 정의 시작을 사용한다.
- 연구원 선택을 비우면 ID와 이름을 함께 비운다. 이후 시작 조건도 충족하지 못한다.
- **담당자 선택·변경은 기존 계약 단계에서만** 제공한다. 범위 정의 이후 재배정은 이번 범위에 추가하지 않는다.
- 예전 이름만 남은 계약 기록은 ‘기존 이름 기록 유지’ 선택지를 제공한다. 사용자가 등록 연구원을 골라 저장하면 ID로 연결한다. 이후 단계의 예전 이름 기록은 읽기 전용이다.
- 연구원 탭에서 등록하고 프로젝트로 돌아오면 입력 중인 고객 이름·범위 내용·선택을 유지하며 선택 목록만 갱신한다.
- 용어사전·연구원 탭 사이를 오가도 프로젝트의 목록/상세와 스크롤을 이어 간다. 실제 브라우저 확인은 아래 한계를 참고한다.

## 4. 기존 기록 보호

- 직접 저장한 고객 담당자·연구원 이름은 샘플 값으로 덮어쓰지 않는다. 명시적으로 저장한 빈 이름도 유지한다.
- 예전 기록에 담당자 **필드 자체가 없을 때**만 해당 샘플의 기본 이름·배정을 보완한다. 읽기만으로 브라우저 저장본을 다시 쓰지 않는다.
- 이름은 있지만 연구원 ID가 없던 기록은 이름을 그대로 두고 ID를 비운다. 샘플과 같은 이름이어도 자동 연결하지 않는다.
- 기존 요청·받은 자료·검토·범위·단계 기록을 초기화하지 않는다.
- `kickoff.test.cjs`의 미배정 계약 검사 입력은 가상 기본 배정 추가 후에도 미배정 사례를 검사하도록 명시적으로 빈 값을 설정했다. 오래된 기록 검사에서는 새 ID 필드도 제거해 실제 구형 형태를 재현한다.

## 5. 보관·실패 규칙

- 연구원 키: `ecoable-lca-manager.researchers.v1`.
- 구조: `{version:1,nextNumber,researchers:[직접 등록 기록]}`. 기본 3명은 코드에 두며 조회 시 합친다. 읽기는 저장하지 않는다.
- ID는 `researcher-sample-1`, `researcher-user-4` 등으로 샘플과 직접 등록을 구분한다.
- 프로젝트 연결은 기존 `scope.v1`에 선택 필드 `researcherId`를 추가한다. `researcherName`은 저장 당시의 이름도 유지한다.
- ID·이름·기준량 등 범위와 단계를 같은 저장 작업에 보관한다. 범위 저장으로 담당 ID를 우회 변경할 수 없다.
- 없는 ID나 연구원 저장소 읽기 실패는 선택 저장을 거절한다. 이름만 같은 다른 사람의 ID로 바뀐 경우에도 이전 화면의 저장·시작은 충돌로 처리한다.
- 명단이 손상되거나 접근이 막히면 등록·선택을 중단하고 안내한다. 집계 화면을 0명·0건 성공으로 위장하지 않는다. 원본을 지우거나 덮어쓰지 않는다.
- 등록 저장 실패 시 입력을 유지하고 번호를 소비하지 않는다. 다른 화면의 등록은 저장 전 최신 저장본을 읽어 이어 간다. 동시 쓰기 잠금·실시간 다중 사용자 동기화는 제공하지 않는다.
- 명단에서 없는 ID가 프로젝트에 남으면 연결 확인으로 분류한다. 삭제·이름 변경·퇴사 처리·재배정·담당 이력은 이번에 구현하지 않는다.
- 연구원 등록은 앱 안의 가상 명단 추가다. 계정 생성·고용 등록·회사 시스템 연결·메일 발송은 없다.

## 6. 사용자 확인 순서

1. 새로고침 후 담당 연구원 탭을 열어 기본 3명과 담당 프로젝트를 확인한다. 수정한 기존 기록이 없다면 건수는 김하늘 3, 박서연 2, 이도윤 2다.
2. 가상 이름으로 새 연구원을 등록한다. 새 번호와 담당 0개를 확인한다.
3. 프로젝트 탭에서 새 프로젝트 또는 계약 단계 프로젝트 상세를 연다.
4. 고객 담당자를 입력하고 등록한 연구원을 선택해 담당자 저장한다.
5. 연구원 탭에서 그 연구원 아래 프로젝트가 나타나는지 확인하고 번호로 상세를 연다.
6. 새로고침 후 연구원 등록·선택이 유지되는지 확인한다.
7. 입력 중 연구원 탭으로 갔다 돌아왔을 때 미저장 입력이 유지되는지, 기존 이름 기록이 덮어써지지 않는지 확인한다.

## 7. 검증과 제한

- `node --test web/tests/*.test.cjs`: **110개 통과**. 기존 96개와 연구원 관련 14개다.
- 가상 기본 배정 일치, 조회 무쓰기·원본 보존, 등록·복원·동명이인·번호 연결, 입력 제한, 저장 실패, 손상 보존, ID 선택과 이름 조회, 잘못된 ID·손상 명단 거절, 선택 해제, 기존 이름과 빈 값 보존, 기본값 보완 무쓰기, ID별 집계·완료·미배정·미연결 구분, 단계 이동 후 복원, 동명이인 ID 변경 충돌을 검사했다.
- 변경 JavaScript 구문·HTML 정적 ID/레이블/ARIA/스크립트 경로·HTTP 200·공백 오류를 확인했다.
- 이전 브라우저 보안 정책의 접근 차단을 우회하지 않았다. **실제 탭 이동·등록·선택·입력 보존·클릭·키보드·작은 화면은 미확인**이다. 자동 검사를 실제 UI 확인으로 설명하지 않는다.

## 8. 파일과 면접 설명

- `researchers.js`: 가상 명단·등록 저장·ID 기준 담당 프로젝트 분류.
- `views/researchers.js`: 등록 폼·인원별 카드·담당 프로젝트와 미연결 안내.
- `data.js`: 7개 가상 고객 담당자·연구원 기본 배정.
- `scope.js`: 연구원 ID 조회 저장·기존 이름 기록 호환·충돌 보호.
- `views/scope.js`: 연구원 선택과 미저장 입력을 유지하는 목록 갱신.
- `app.js`: 세 메뉴와 상세 이동, 저장소 연결.

면접 설명 예: ‘연구원을 이름으로만 기록하면 동명이인이나 여러 프로젝트의 담당 집계가 어려워 고유 번호로 분리했습니다. 명단에 연구원을 등록한 뒤 프로젝트에서 선택하고, 같은 ID로 연결된 프로젝트만 모아 보여줍니다. 예전 이름 기록은 자동 연결해 잘못 배정하지 않고 그대로 보존했습니다.’
