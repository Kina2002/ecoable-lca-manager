# WEB-054 요청문 발송 기록

사용자 승인 순서: 요청문 발송 기록 → 정보 확인 안내문 → 프로젝트 추가정보 편집.

## 목적과 사용법

자료 요청 탭에서 요청문을 만들고 수정·복사한 뒤 외부 메일이나 메신저로 실제 보낸다. 편집기 아래 ‘실제로 보낸 요청문 기록’에서 받는 사람, 메일/메신저/기타, 실제 보낸 한국 날짜·시각, 기록 담당자를 적고 발송 확인에 체크한 후 ‘보냈어요’를 누른다. 앱은 직접 메시지를 발송하지 않는다.

보낸 당시 회사·제품, 요청문 종류, 대상 자료 번호, 편집한 제목·본문, 실제 발송 시각과 기록 시각을 사본으로 보관한다. 과거 이력은 접어서 조회하며 최신 요청이나 자료 상태가 바뀌어도 사본을 고치지 않는다. 자료 제출·승인이나 단계는 바꾸지 않는다. 복사만으로는 발송 기록을 만들지 않는다.

## 규칙·보호

- 실제 보낸 시각은 미래일 수 없다. 받는 사람·담당자·제목·본문과 대상이 필요하며 `[입력 필요: ...]`가 남으면 기록을 막는다.
- 같은 생성 요청문은 한 번만 기록한다. 다른 발송은 새 요청문을 생성해 별도 기록한다. 수정 차수도 확인해 다른 창의 발송 기록을 덮지 않는다.
- 발송 후 업무 정보가 바뀌었더라도 실제로 보냈다고 확인한 내용은 기록할 수 있다. 이때 최신 업무 기준과 다르다는 표시를 남긴다. 이 기록은 최신 자료 요청문을 새로 만드는 동작과 구분한다.
- 기록은 수정·삭제 UI 없이 보관한다. 프로젝트를 영구 삭제하면 그 프로젝트의 발송 이력도 함께 삭제되며 삭제 전 건수를 알린다.

## 저장·백업

기존 `requests.v1`에 선택적인 `messageLog`를 추가한다. 기존 백업 키를 그대로 사용하고 옛 기록·백업은 발송 0건으로 읽는다. 자료 요청을 추가·수정·삭제할 때도 발송 이력을 보존한다. 백업 미리보기에 발송 건수를 표시하고 복원 검증도 수행한다. 손상된 발송 이력은 0건으로 숨기지 않고 요청 저장소 읽기 실패로 알리며 원문을 보존한다.

## 검증

전체 자동검사 **249개** 통과. 사본 저장·재읽기와 자료 상태 보존, 중복·미래 시각·확인 누락·다른 프로젝트·입력 필요 표시 차단, 손상 기록 보호, 백업 검증·프로젝트 삭제 계획의 격리를 검사했다. 변경 JavaScript 구문·Git 공백·정적 파일 응답을 확인한다. 실제 브라우저 클릭·입력·외부 메일 발송은 시험하지 않았다.

면접 설명: “문장을 만들거나 복사한 것과 실제 발송은 다릅니다. 외부에서 보낸 뒤 담당자가 확인해 발송 시각과 정확한 문구를 보관하도록 했습니다. 고객이 나중에 자료를 보내도 과거 발송 기록은 그대로 남고, 발송 버튼만으로 자료가 제출된 것으로 바뀌지 않습니다.”
