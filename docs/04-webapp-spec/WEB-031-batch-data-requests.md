# WEB-031 자료 요청 일괄 생성

작성일: 2026-10-18

## 1. 합의와 목적

사용자가 입력 부담 개선 이후 다음 추천 기능 구현을 승인했다. 앞서 정한 순서의 두 번째인 자료 요청 일괄 생성을 구현한다. 여러 자료 구분을 선택하고 공통 제출 기한을 한 번 정해 요청을 등록한다. 기존 개별 등록, 두 위치의 자료 상태 필터, 수집·검토 완료 확인, 별도 단계 이동 정책을 유지한다.

## 2. 화면과 사용 방법

1. 프로젝트 상세의 자료 요청 탭에서 **여러 자료 한 번에 등록**을 펼친다. 요청이 없는 쓰기 가능 프로젝트는 처음부터 펼쳐 보인다.
2. 11개 자료 구분 중 필요한 것만 선택한다. 미등록 구분 전체 선택과 선택 해제를 제공한다. 전체 선택을 필수로 요구하지 않는다.
3. 공통 제출 기한을 숫자 8자리, 오늘 또는 달력으로 입력한다. 프로젝트의 자료 수집 마감일이 있으면 사용 버튼으로 가져올 수 있다. 수집 마감일 자체나 기존 요청 기한을 바꾸지 않는다.
4. 각 선택 항목의 기본 요청 문장을 바로 쓰거나 **기본 요청 내용 확인·수정**을 펼쳐 편집한다. 각 1,000자 이내이며 구분별 지침 근거·원문 링크·확인일도 함께 제공한다.
5. 선택 수·새 등록 수·건너뛸 수를 확인하고 일괄 등록한다. 기존 **자료 하나 등록**도 계속 사용할 수 있다.

메일 발송·고객 통보·자동 승인·프로젝트 단계 이동은 수행하지 않는다. 과거 기한 허용과 각 자료의 요청 상태·기한 계산은 기존 규칙을 따른다.

## 3. 저장 규칙

- `requests.createStore().addMany(projectId, {dueDate, items:[{categoryKey,detail}]})`를 제공한다. 결과는 `{ok:true,items:[새 기록],skipped:[{categoryKey,id}]}` 또는 오류다.
- 알려진 프로젝트, 유효 날짜, 1~11개의 중복 없는 유효 구분, 새로 등록할 항목의 공백 아닌 1,000자 이내 내용을 확인한다.
- 저장 직전에 현재 저장본을 한 번 읽는다. 해당 프로젝트의 삭제되지 않은 같은 구분은 건너뛰며 기존 내용·기한·제출·검토·승인을 바꾸지 않는다.
- 삭제된 요청은 기존 삭제 이력에 보존한다. 새로 선택하면 새 번호로 생성하며, 같은 구분의 활성 요청이 있으면 과거 기록 복원은 기존 규칙대로 막는다.
- 새 항목에 연속 DRQ 번호, 동일 등록 시각, 구분별 지침 사본, 요청 상태와 공통 기한을 부여한다. 모든 새 항목을 준비한 뒤 기존 `ecoable-lca-manager.requests.v1`에 **setItem 한 번**으로 저장한다. 개별 add의 반복 호출은 하지 않는다.
- 검증 실패·저장 공간 오류 때 일부 항목만 등록하지 않는다. 전부 기존 구분이면 쓰기와 번호 증가 없이 건너뛴 사실만 알린다.
- 기존 데이터 구조·버전·다른 프로젝트·삭제 기록을 보존한다. 별도 저장 키나 자동 단계 이동은 추가하지 않는다.
- 기존 도메인의 단계 검사로 9단계 이후 쓰기와 단계 확인 실패 시 쓰기를 막는다. 화면도 같은 읽기 전용 정책을 따른다.
- 이 한 번의 로컬 저장은 여러 탭의 다른 쓰기를 직렬화하는 서버 트랜잭션은 아니다. 기존 요청 쓰기에는 탭 간 Web Lock이 없으며 동시 쓰기의 완전한 보호는 이번에 구현하지 않았다.

## 4. 입력과 기존 화면 보존

- 선택을 풀었다 다시 선택해도 수정한 문장을 유지한다. 일반 목록 갱신·필터 전환·저장 실패 때 공통 날짜와 선택·문장을 유지한다.
- 성공하면 이번 선택을 해제하고 공통 기한과 문장은 유지한다. 새 요청과 건너뛴 구분을 상태 영역에 안내한다.
- 내용 오류는 해당 펼침 영역을 열고 첫 오류에 초점을 둔다. 저장 실패 시에는 성공 문구를 표시하지 않는다.
- 현재 상태 필터를 유지한다. 새 요청은 요청 상태이므로 승인 등 다른 필터에서는 숨겨질 수 있음을 안내한다.
- 기존 요청 목록·구분별 중복 표시·상세 요청 건수·상위 수집 목록과 기존 콜백을 연결한다. 수집·검토 완료 확인은 기존 별도 컨테이너에 유지한다.
- 상세 화면을 닫거나 새로고침하면 미저장 초안은 초기화되는 기존 정책이다. 별도 임시 저장은 아니다.

## 5. 구현 파일

- 저장: `web/js/requests.js`
- 일괄 입력: `web/js/views/request-batch.js`
- 기존 요청 화면 연결: `web/js/views/requests.js`
- 로딩·개별 입력 제목: `web/index.html`
- 두 열 항목과 좁은 화면 한 열 스타일: `web/css/app.css`

## 6. 확인과 제한

- JavaScript 구문·Git 공백 검사를 확인했다.
- 별도 localhost 탭의 해든솔라 가상 프로젝트에서 요청이 없을 때 펼친 일괄 입력, 11개 구분·공통 기한·오늘/달력·기존 개별 등록·상태 필터의 초기 표시를 확인했다. 사용자 127.0.0.1 탭과 저장 데이터를 수정하지 않았다.
- 테스트 추가·실행은 하지 않았다. 실제 선택·등록·수정 문장 저장·중복 건너뛰기·원자적 실패·다시 열기·단계 제한·기한 불러오기·좁은 화면과 키보드 전체 흐름의 실행 확인은 남아 있다.
- 구문과 초기 표시 확인을 기능 전체의 실행 검증 완료로 설명하지 않는다. 이전 SPEC의 미확인 범위도 그대로 남는다.
