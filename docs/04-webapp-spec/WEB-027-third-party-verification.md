# WEB-027 제3자 검증 차수·지적·보완 관리

- 작성일: 2026-10-18
- 승인 범위: 제3자 검증 시작(7→8), 검증기관·담당자, 차수별 지적·보완 기한·답변·처리 상태, 수정 보고서 연결. 사용자가 “구현해보자”로 승인했다.
- F-01 단계 이동과 F-08 제3자 검증 부분이다. F-08 전체 완료나 실제 검증·인증 판정 기능은 아니다.

## 1. 쉬운 사용 흐름

1. 보고서 단계에서 고객 검토 의견을 모두 종결하고 최신 자료·계산·해석에 맞는 보고서를 보관한다.
2. 상세의 **제3자 검증** 탭에서 검증기관, 외부 검증 담당자, 기록 담당자를 적는다. 검토 준비 확인에 체크하고 **제3자 검증 시작 · 8단계로**를 누른다.
3. 1차에서 받은 지적과 보완 기한, 기록 담당자를 등록한다. 이 지적이 대상으로 삼은 보고서는 1차 시작 당시의 버전으로 고정된다.
4. 담당자가 보완 내용·답변을 적는다. 보고서를 수정했다면 보고서 탭에서 새 버전을 보관한 뒤 지적 답변의 수정 보고서로 선택한다.
5. 검증자가 답변과 보완을 확인했다는 내용·종결 근거를 적고 확인 체크 후 지적을 종결한다.
6. 현재 차수의 모든 지적을 종결하고 검토 완료를 확인한 뒤 2차·3차 등을 시작한다. 번호는 자동으로 1씩 증가한다.

예: v1을 검토한 1차 지적 → 운송 근거 보완 → v2 보관 → 답변에 v2 연결 → 검증자 확인 근거를 남겨 종결 → v2를 대상으로 2차 시작.

## 2. 시작·차수 규칙

- 첫 차수는 보고서(7) 또는 기존 제3자 검증 샘플(8)에서만 시작한다. 첫 차수 저장과 8단계 진입은 같은 저장 작업이다.
- 최신 보고서가 존재하고 현재 승인 자료·계산·해석과 일치해야 한다. 보고서나 근거가 바뀌면 기준을 다시 확인해야 한다.
- 고객 의견은 모두 종결되어야 한다. 의견 0건도 허용하지만 담당자가 준비 확인에 체크한다. 고객 의견 저장소를 읽지 못하면 시작을 막는다.
- 후속 차수는 현재 차수의 지적이 모두 종결되어야 시작한다. 지적 0건도 별도 검토 완료 확인 후 다음 차수를 시작할 수 있다.
- 다음 차수의 검토 보고서는 그때의 최신 유효 보고서다. 설명만으로 해결했다면 같은 보고서로 다시 검토할 수 있다. 버전 번호가 줄어드는 차수는 허용하지 않는다.
- 차수별 기관·검증자·기록자·메모·시작 시각과 검토 보고서 번호·제목을 보관한다. 차수 정보를 덮어쓰거나 삭제하지 않는다.
- 이전 차수는 읽기 전용이다. 추가 지적과 처리는 현재 차수에 남긴다. 차수 선택과 처리 상태 필터를 조합해 볼 수 있다.

## 3. 지적·답변·종결

| 동작 | 필수 조건 | 저장 결과 |
| --- | --- | --- |
| 지적 등록 | 현재 차수, 내용·보완 기한·기록자 | 열림, VER-001-001 등 차수별 자동 번호 |
| 답변 저장 | 종결 전, 답변·담당자·처리 방법 | 답변됨, 이전 답변도 이력에 보존 |
| 보고서 수정 연결 | 원래 검토 보고서보다 나중에 보관한 같은 프로젝트 버전 | 수정 보고서 번호 보관 |
| 지적 종결 | 저장된 답변, 확정 처리 방법, 검증자 확인·종결 근거, 확인 체크 | 종결 |
| 다시 열기 | 현재 차수의 종결 지적, 담당자·재개 사유 | 열림, 현재 처리 방법 미정으로 복귀 |

- 처리 방법: 미정 / 보고서 수정 / 설명으로 해결. 미정으로 답변은 보관하지만 종결하지 못한다.
- 보완 기한은 연월일 8자리 또는 YYYY-MM-DD로 입력한다. 화면 갱신 때 D-day를 계산하고 종결은 종결로 표시한다. 기한이 지났다고 검증 실패로 자동 판정하지 않는다.
- 최초 지적·대상 보고서·보완 기한은 보존한다. 이들을 직접 수정·삭제하는 화면은 이번에 추가하지 않았다.
- 원문·답변은 각각 3,000자, 사람 이름 100자, 기관 200자, 메모·종결 근거·재개 사유는 1,000자까지다. 차수 메모만 선택 사항이다.
- 등록·답변·종결·재개마다 담당자와 시각을 이력에 추가한다. 이름은 직접 입력한 기록이며 인증된 로그인 신원은 아니다.
- 지적 카드에서 원래 검토 보고서와 수정 보고서로 이동할 수 있다. 보고서 탭은 선택 버전의 당시 본문과 근거를 보여준다.
- 지적 종결은 담당자가 검증자 확인 근거를 기록하는 동작이다. 앱에서 외부 검증자의 결정을 대신하거나 검증 통과·인증을 자동 확정하지 않는다.

## 4. 검증 중 보고서 보완

제3자 검증(8)에서도 외부 계산 결과·해석·보고서를 보완할 수 있도록, 기존 해석 저장 허용 단계에 8을 추가하고 보고서 새 버전 저장도 7·8에서 허용했다. 근거 변경 감지·기준 다시 확인·작성 확인·버전 충돌 보호·과거본 내보내기 구분은 유지한다. 수정 전 보고서 사본은 그대로 보관한다.

고객 검토는 기존대로 7단계만 쓰고 검증 시작 후에는 읽기 전용이다. 제3자 검증 중 새 고객 의견을 접수하는 정책이나 8→7 되돌리기는 이번에 확장하지 않았다. 기존 자료 요청의 두 상태 필터와 보고서·해석 입력 초안은 유지한다.

## 5. 저장 구조와 단계 복원

새 키 `ecoable-lca-manager.verification.v1`:

```text
{ version: 1, records: {
  projectId: { revision, rounds: [차수 정보], issues: [원문·기한·대상 보고서·events] }
} }
```

- 유효한 검증 기록이 존재하면 그 프로젝트의 유효 단계가 최소 8이다. 기존 scope.v1의 1~7 단계 기록과 합쳐 `scope.load/currentStage`에서 계산한다. 기존 scope 기록은 변환·덮어쓰기하지 않는다.
- 따라서 첫 차수와 8단계 진입은 새 키의 단일 setItem으로 저장한다. 쓰기 실패 시 첫 차수도 생기지 않고 단계도 바뀌지 않는다. 새로고침 시 검증 기록에서 8을 복원한다. 기존 8단계 샘플은 최신 보고서를 먼저 준비해 1차 정보를 보관할 수 있다.
- 전체 기록 리비전은 차수 수와 모든 지적 이벤트 수의 합이다. 읽을 때 번호·리비전·시간 순서·프로젝트·보고서 관계·이벤트 상태 전이·과거 차수의 종결 상태를 검사한다. 손상된 JSON을 빈 기록으로 덮어쓰지 않는다.
- 차수·지적 등록은 예상 전체 리비전을 확인한다. 답변·종결·재개는 전체 리비전과 해당 지적 이벤트 리비전도 확인한다. 다른 탭에서 기록이 바뀌면 입력을 유지하고 저장을 중단한다.
- 검증 기준·지적 등록 기준 다시 확인은 작성 내용을 유지하며 최신 기록에 기준을 맞춘다. 최신 답변 불러오기는 사용자가 눌러 그 지적의 미저장 입력을 초기화한다.
- Web Locks 지원 시 보고서 버전·고객 의견·검증 쓰기에 같은 `review-workflow-write` 잠금을 사용한다. 최신 코드가 열린 탭 사이에서 고객 의견 추가와 검증 시작, 보고서 버전 추가 등을 직렬화한다. 미지원 환경은 예상 리비전 검사만 적용하므로 완전한 동시 쓰기 원자성을 보장하지 않는다. 원자료·계산·해석의 기존 쓰기를 모두 포괄하는 서버 트랜잭션은 아니다.
- 저장 시 최신 단계·보고서·고객 의견·차수·리비전을 다시 읽는다. 저장 공간 오류와 중복 클릭을 처리하며 입력과 기존 기록을 보존한다.
- 연결 보고서가 없거나 범위·검증·보고서 형식이 손상되면 저장과 단계 전환을 막는다. 현재 근거만 달라진 경우 유효한 보관 보고서의 기존 지적·답변은 조회·처리할 수 있고, 다음 차수 시작은 최신 보고서를 준비한 뒤 가능하다.
- 탭·필터 전환에서 미저장 입력을 유지한다. 새로고침·상세 닫기 후의 미저장 입력 복원과 전체 백업·다른 기기 동기화는 제공하지 않는다.
- 기존 여덟 키·저장본을 유지한다. 공통 답변 이벤트 규칙은 review-workflow.js로 분리했으며 기존 고객 의견 형식과 상태 규칙은 유지했다.

## 6. 확인 범위와 한계

- 변경 JavaScript의 구문과 Git 공백 확인을 수행했다.
- 별도 localhost의 기존 가상 프로젝트에서 새 제3자 검증 탭, 최신 v1 기준·고객 의견 0건 준비 표시, 검증기관·담당자·확인 입력, 차수 전 지적 등록 비활성·빈 차수/필터 초기 화면 표시를 확인했다. 사용자 127.0.0.1의 저장 기록을 변경하지 않았다.
- 이번 작업에서 테스트를 추가하거나 실행하지 않았다. 실제 7→8 저장·복원, 지적·답변·보고서 수정 연결·종결·재개·2차 시작, 저장 실패·동시 쓰기 실행 확인은 남아 있다. 기존 테스트 개수를 이번 통과 수로 주장하지 않는다.
- PDF·Word 재생성·렌더, 기존 흐름의 회귀 실행도 이번에 하지 않았다. 문서 내보내기 확인 한계는 WEB-023을 따른다.

## 7. 후속 범위

8→9 인증·등록, 공식 검증 결과·완료 문서, 기관별 요구사항·라운드 승인, 자료 질의 통합 유형, 첨부·메일·고객/검증자 로그인, 기한 수정·알림, 범위 재협의, 서버 저장은 별도 합의한다. 내부 LCA 계산과 AI는 기본 기능 구현 후 검토한다.
