# 다음 작업: UI 사용성 개선 인수인계

정리일: 2026-10-19 (한국 시간)

**상태: 사용자 승인으로 [WEB-042](WEB-042-compact-workspace-ui.md)에 1차 반영됨. 이 문서는 후속 UI 조정 기준이며 구현/확인 범위는 WEB-042를 따른다.**

## 사용자의 문제 제기

- 쓸데없이 큰 버튼과 블록 때문에 화면을 낭비한다.
- 한 페이지가 길어 오래 스크롤해야 한다. 최대한 한 화면에 정보가 보이기를 원한다.
- 주요 정보가 눈에 잘 들어오지 않는다.
- 다른 노트북에서 이 작업을 바로 이어가고 싶다.

새 업무 기능보다 위 세 문제를 먼저 개선한다. 화면의 실제 높이·정보 우선순위·불필요한 반복을 함께 다룬다.

## 첫 작업 순서

1. 최신 코드를 받고 미리보기를 실행한다. `CONTINUE-HERE.md`를 따른다.
2. 홈, 프로젝트 목록, 라온소재 상세의 개요·범위/자료 요청을 읽고 세로 공간을 많이 쓰는 부분을 찾는다. 미저장 입력이 있는 사용자 탭을 임의로 새로고침하지 않는다.
3. 공통 여백·제목·버튼 규격부터 정리한다. 기능별 CSS 뒤에 재정의가 많으므로 마지막 규칙까지 추적해 바꾼다.
4. 홈 → 프로젝트 목록 → 상세 상단/자료 요청 순서로 첫 화면의 핵심 정보 배치를 정리한다.
5. 같은 방식으로 계산·해석·보고서·고객 검토·검토/검증·인증/등록·연구원·설정 화면에 적용한다. 긴 폼을 한 번에 모두 펼쳐 놓지 않는다.
6. 변경 범위와 남은 확인을 SPEC에 기록하고 일반 push한다. UI 개선과 관계없는 업무 기능을 끼워 넣지 않는다.

## 적용할 방향

| 문제 | 구현 방향 |
| --- | --- |
| 큰 버튼 | 일반 동작은 내용 너비에 맞춘 작은 버튼으로 통일하고 주요 저장/다음 단계만 강조한다. grid/flex의 늘어남 때문에 버튼이 큰 블록이 되지 않게 정렬을 확인한다. |
| 과한 카드·상단 여백 | 제목·설명·카드 안팎 여백과 상단 바 높이를 정리한다. 큰 카드 속에 또 큰 카드를 반복하지 않는다. |
| 긴 프로젝트 상세 | 회사/제품·현재 단계·목표/수집 기한·핵심 건수를 짧은 상단 요약으로 배치한다. 같은 정보를 여러 곳에 크게 반복하지 않는다. 탭에 도달하기 전 긴 스크롤이 없게 한다. |
| 긴 자료 요청 | 수집/검토 완료 조건을 짧은 상태 요약과 주요 행동으로 정리한다. 요청문·등록 폼은 기존 접기를 유지하고, 자료는 상태·기한·값/증빙·다음 행동을 짧은 행에서 확인하게 한다. 긴 근거/메모는 필요할 때 펼친다. |
| 정보가 눈에 안 들어옴 | 회사/제품·단계·기한·미처리 수를 먼저 읽히게 한다. 진행·완료·지연/보완의 의미를 라벨과 숫자로 구분한다. 작은 회색 글씨에 핵심 정보를 숨기지 않는다. |
| 홈의 긴 목록 | 요약 수치와 우선 처리할 업무가 한눈에 이어지게 배치한다. 적절한 열 배치·짧은 행·더 보기로 높이를 줄인다. 기존 관련 화면 이동을 유지한다. |
| 긴 설명과 이력 | 초보자가 이해할 안내는 남기고, 반복 안내·상세 설명·과거 이력은 도움말/접기 안에 둔다. 저장 실패·필수 값·주의 사항은 숨기지 않는다. |

## 화면 크기와 가독성

- 우선 노트북 1366×768 및 1280×720, 브라우저 확대 100%에서 핵심 요약과 첫 업무 목록이 보이도록 목표를 잡는다. 실제 뷰포트 높이는 도구 모음에 따라 다르므로 확인 없이 달성했다고 쓰지 않는다.
- 한 화면에 모든 상세 본문을 억지로 넣는 방식은 피한다. 첫 화면에서 판단과 다음 행동을 할 수 있고, 상세는 선택해서 보게 한다.
- 긴 내용을 `overflow: hidden`으로 자르거나 글씨를 과도하게 축소하지 않는다. 중첩 스크롤 영역을 여기저기 만들지 않는다.
- 좁은 화면에서는 적절히 줄바꿈/한 열 배치하고 버튼·체크박스는 누르기 편한 영역을 유지한다.
- 키보드 초점·레이블·펼침 상태를 제공하고, 색상만으로 상태를 구분하지 않는다.

## 유지할 동작

- 기존 저장 키/형식, 연구원 ID와 담당 배정, 프로젝트/자료의 단계·상태 조건.
- 상단 수집 단계의 자료 필터와 회사별 상세 자료 필터 **둘 다**, 서로 독립적인 선택 상태.
- 작성 중인 입력·요청문 수정 내용·펼침 상태. 목록 갱신을 위해 폼 전체를 다시 만들지 않는다.
- 사용자 입력, 보고서 과거 사본·버전·변경 이력, 고객 의견/검증 차수와 연결.
- 위험한 삭제/복원의 기존 재확인, 실패 시 입력 유지와 오래된 기록 쓰기 차단.
- 회사 옆 가상 표시와 포트폴리오 안내. 실제 업무 데이터와 기본 가상 사례를 혼동시키지 않는다.

## 주로 읽고 수정할 파일

- `web/css/app.css`: 공통 여백/버튼/카드/탭/목록/반응형. `main`, `.topbar`, `.page-heading`, `.stage-overview`, `.stage-filter`, `.detail-card`, `.primary-button`, `.request-action-button`부터 확인한다. 현 코드에는 main 상단 43px, page-heading 하단 32px, 단계 버튼 최소 높이 88px, detail-card padding 27/28px 등 누적 여백이 있다.
- `web/index.html`: 주 메뉴·상세 패널·폼·dialog의 고정 구조.
- `web/js/views/project-detail.js`, `project-list.js`, `dashboard.js`, `tasks.js`: 요약/목록 배치와 관련 연결을 확인한다.
- `web/js/views/requests.js`, `request-batch.js`, `request-message.js`: 상태 요약·자료 목록·접기 폼. 두 자료 필터와 초안 보호에 주의한다.
- `web/js/views/researchers.js`: WEB-041 한 줄 표와 등록/프로젝트 접기. 현재 사용자 선호의 배치 예시다.
- 그 외 상세 탭은 `web/js/app.js`의 바인딩과 실제 view 파일을 먼저 찾는다. CSS로만 처리 가능한 부분은 도메인 저장 로직을 변경하지 않는다.

## 확인·보고 방법

첫 화면에서 주요 정보가 보이는지, 버튼/카드 높이가 줄었는지, 긴 내용 접근과 저장/다음 행동이 가능한지를 실제 화면으로 확인한다. 확인한 화면 크기·변경 전후·남은 제한을 기록한다. 사용자 기록을 초기화하거나 다른 노트북으로 이동했다고 추정하지 않는다. 자동 테스트는 사용자가 요청한 범위에 맞춰 추가/실행하고, 이전 217개 결과를 이번 변경 결과로 재사용하지 않는다.
