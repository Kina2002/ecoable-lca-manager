# WEB-028 검증 완료 기록과 인증·등록 관리

- 작성일: 2026-10-18
- 사용자 승인: 검증 완료 근거·별도 8→9·제출 상태·최종 번호와 날짜 제안을 하위 에이전트에게 구현하도록 명시했다.
- F-01 단계 연결, F-12 인증·등록의 부분 구현이다. 인증 의무 여부나 기관의 공식 판정을 앱이 결정하지 않는다.

## 1. 사용 흐름

1. **제3자 검증**에서 차수를 기록하고 모든 지적을 종결한다. 필요하면 8단계에서 자료·외부 계산 결과·해석·보고서를 보완한다.
2. **인증·등록** 탭에서 검증 완료일·검증 결과 문서 이름·기록 담당자·완료 확인 근거를 적고 최종 보고서 확인에 체크한다.
3. **검증 완료 기록 보관**으로 당시 최종 보고서 전체와 검증 차수·지적·처리 이력 사본을 보관한다. 단계는 아직 8이다.
4. 유형(인증/등록/고객 제출), 제출기관·고객, 제도·제출 요구명, 기록자와 사유를 적는다. 별도 확인 후 **인증·등록 준비 시작 · 9단계로**를 누른다.
5. 제출일과 진행 상태를 기록한다. 보완 요구는 메모에 남기고 재제출 시 다시 **제출 완료**로 기록한다.
6. 승인·등록을 기록할 때 번호와 발급·확인일을 남긴다. 고객 제출은 접수·확인 번호와 확인일을 기록한다. 반려도 사유와 함께 남긴다.

모든 LCA가 인증을 받는 것은 아니다. 프로젝트별 요구에 따라 등록 또는 고객 제출을 선택할 수 있다. 문서 파일은 이름만 기록하며 파일 내용은 업로드하지 않는다.

## 2. 완료·이동 조건

- 8단계에서 실제 검증 차수가 최소 하나 있어야 한다. 기존 8단계 가상 샘플도 보고서와 첫 차수부터 기록해야 한다.
- 고객 의견과 검증 저장소를 읽을 수 있고 미종결 고객 의견·검증 지적이 없어야 한다. 지적 0건도 담당자의 완료 확인과 근거가 필요하다.
- 최신 보고서가 현재 승인 자료·계산·해석과 일치해야 한다. 완료 보관 시 최신 보고서 리비전·근거 키·검증 리비전을 다시 비교한다.
- 완료 기록 후 8단계에서 보고서나 지적을 보완하면 이전 완료 사본은 남기고 **완료 근거 새로 보관**을 해야 한다. 완료 근거와 현재 보고서·검증 기록이 다르면 8→9를 막는다.
- 완료 근거 보관과 8→9 이동은 별도 동작이다. 첫 `started` 이벤트와 제출 준비 정보, 9단계 근거는 같은 키의 한 번의 쓰기로 보관한다. 실패하면 단계가 바뀌지 않는다.
- 9→10, 단계 되돌리기, 기관별 자동 심사·신청·메일 전송은 구현하지 않았다.

## 3. 상태와 필수 입력

| 현재 상태 | 허용하는 다음 상태 |
| --- | --- |
| 제출 준비 | 제출 준비, 제출 완료 |
| 제출 완료 | 제출 완료, 보완 요청, 승인·등록, 반려 |
| 보완 요청 | 보완 요청, 제출 완료, 반려 |
| 승인·등록 | 승인·등록 (정보 정정 이력) |
| 반려 | 반려 (정보 정정 이력) |

- 매번 전체 진행 정보와 기록자·확인 근거/변경 사유를 사본으로 추가한다. 같은 상태로 오기를 고쳐도 이전 정보는 이력에 남는다.
- 유형·제출기관/고객·제도/요구명은 필수다. 제출 완료 이후에는 제출일, 승인·등록에는 번호와 발급·확인일이 필수다. 발급일이 제출일보다 빠르면 막는다.
- 날짜는 8자리 입력 또는 YYYY-MM-DD를 받는다. 완료일도 올바른 달력 날짜여야 한다. 이름 100자, 기관·제도·번호·문서 이름 각 200자, 사유 1,000자, 메모 2,000자까지다.
- 반려 뒤 새 신청, 승인 취소, 다수 제도 동시 제출은 이번 구조에 추가하지 않았다. 한 프로젝트의 한 제출 절차를 기록한다.

## 4. 이전 단계와 보완 정책

9단계 진입 후에는 완료 근거를 고정한다. 자료 요청 등록·삭제·복원·받은 자료 재기록·검토, 외부 계산 결과 저장, 해석·새 보고서 저장, 검증 차수·지적 처리는 읽기 전용이다. 자료 요약·검토 요약, 보고서와 기존 내보내기, 고객 의견·검증 기록은 조회할 수 있다. 기존 필터와 입력 초안은 유지한다.

제출 후 **보완 요청**은 요구 내용·응답/보완 메모와 재제출 날짜·상태를 기록한다. 이 단계에서 평가 자료·보고서 자체를 다시 만드는 흐름은 포함하지 않았다. 보고서 재작성이 필요한 경우의 통제된 9→8 재개·새 완료 근거·다시 제출하는 차수 연결은 후속 합의가 필요하다. 현재 상태만 바꿔 이미 제출한 최종 보고서의 근거를 묵시적으로 바꾸지 않는다.

## 5. 저장·실패·동시 쓰기

새 키 `ecoable-lca-manager.certification.v1`:

```text
{ version: 1, records: { projectId: {
  revision: 이벤트 개수,
  events: [
    completed: 완료일·문서이름·전체 보고서 사본·전체 검증 기록 사본·근거·기록자·시각,
    started: 제출 준비·진행 정보 사본·근거·기록자·시각,
    updated: 상태·진행 정보 사본·변경 사유·기록자·시각
  ]
} } }
```

- 기존 아홉 키와 저장본은 유지한다. 손상된 JSON·잘못된 보고서/검증 사본·날짜·상태 순서·리비전은 빈 기록으로 덮어쓰지 않는다.
- `currentStage`는 이 키의 유효 `started`를 9단계 근거로 반환한다. `app.js`가 검증 8단계와 합쳐 scope.load/currentStage에 전달한다. 범위 저장소를 조회하는 순환 호출을 만들지 않는다.
- 예상 리비전과 최신 완료 근거를 다시 확인한다. 다른 탭에서 변경되면 입력을 유지하고 저장을 중단한다. **최신 기준 다시 확인**은 입력을 유지하며 확인 체크를 해제한다.
- 보고서·고객 의견·검증과 같은 Web Lock으로 인증·등록 쓰기를 직렬화한다. 미지원 환경은 리비전 검사만 적용한다. 기존 원자료·계산·해석 쓰기를 모두 포괄하는 서버 트랜잭션은 아니며, 구형 코드를 연 탭까지 강제하지 못한다.
- 저장 공간 오류·중복 클릭을 처리한다. 쓰기 성공 후 단계·목록 건수·화면을 갱신한다. 브라우저 로컬 저장이며 로그인 신원·서버 감사 기록·백업·기기 동기화는 아니다.

## 6. 확인 범위

- 변경 JavaScript의 `node --check`와 `git diff --check`를 수행했다.
- 별도 localhost 가상 저장 공간에서 7단계 프로젝트의 새 인증·등록 탭, 기존 최신 v1 표시, 단계 조건 안내, 완료일·문서 이름·진행 정보·상태 및 비활성 조건의 초기 화면을 확인했다. 브라우저 오류 로그는 없었다. 사용자 127.0.0.1 입력 기록은 바꾸지 않았다.
- 테스트는 추가하거나 실행하지 않았다. 실제 완료 저장·사본 복원·8→9·진행 상태 저장·종결 필수값·동시 쓰기·실패 복원·9단계 이전 입력 보호의 실행 확인은 남아 있다. 구문 검사와 초기 화면을 기능 흐름 검증으로 주장하지 않는다.
- 기존 PDF·Word 생성과 이전 기능의 회귀 실행도 이번 작업에서 하지 않았다.

## 7. 후속 범위

만료일 계산·알림, 갱신·매년 점검, 9→10, 다수 제도·제출 차수, 9→8 재개·새 보고서로 재제출, 파일 첨부·기관 연동·메일·서버 저장은 후속이다. 내부 LCA 계산과 AI는 기본 기능 구현 후 검토한다.
