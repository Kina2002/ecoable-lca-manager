# WEB-008 받은 자료 검토·보완 요청·승인

- 기준: 설계서 v02 F-04의 검토 상태와 보완 사유, WEB-007 받은 자료 기록.
- 합의: 담당자가 받은 자료를 보고 요청한 기간·제품/사업장·항목과 증빙이 맞는지 세 가지를 확인한다.
- 범위: 검토 시작, 체크·메모 저장, 보완 요청과 필수 사유, 전 항목 확인 후 승인, 받은 자료 재기록 시 검토 초기화.
- 확인일: 2026-10-16. 구현·자동 검사 45개·HTML 연결 검사를 완료했다. 실제 브라우저 화면 확인은 아래 제한을 따른다.

## 1. 왜 만드는가

자료를 받았다는 것과 요청에 맞는 자료라는 것은 다르다.
예를 들어 1~12월 고지서를 요청했는데 12월분이 없다면, ‘제출됨’이어도 자료를 더 받아야 한다.
담당자가 확인한 내용과 다시 받아야 하는 이유를 요청에 연결해 남긴다.

검토의 중심은 ‘받은 자료가 요청에 맞는가’다.
프로그램에 옮겨 적은 숫자가 원본과 같은지 확인하는 항목은 사용자의 설명 확인 후 이번 체크 목록에서 제외했다.
검토자는 회사에서 받은 원본 파일을 별도로 열어 확인한다. 앱은 파일 내용이나 진위를 자동 판정하지 않는다.

## 2. 세 가지 확인 항목

| 키 | 화면 문구 | 확인 목적 |
|---|---|---|
| period | 요청한 기간의 자료인가요? | 요구한 월·연도 등에 해당하는지 확인 |
| scope | 요청한 제품·사업장에 해당하는 자료인가요? | 다른 제품·공장의 자료와 혼동하지 않기 |
| complete | 요청한 항목과 증빙이 빠짐없이 있나요? | 요청 내용에 필요한 자료가 갖춰졌는지 확인 |

체크는 담당자가 확인했다는 기록이다. 이 목록은 우리 시연 앱에서 정한 기본 확인 목록이며 회사 공식 심사 기준이나 인증 기준이 아니다.
자료의 상세 행·실제 증빙 연결과 자동 누락 판정은 사용자가 나중에 구현하기로 한 범위로 유지한다.

## 3. 사용 흐름

1. 프로젝트 상세 → 자료 요청에서 받은 자료가 ‘제출됨’인 요청의 ‘검토 시작’을 누른다.
2. 브라우저 저장에 성공하면 ‘검토 중’으로 바뀌고 검토 창을 연다.
3. 요청 내용과 받은 값·기간·증빙 파일 이름을 같은 창에서 확인한다.
4. 원본을 보고 세 항목을 체크하고, 필요한 메모나 보완 사유를 적는다.
5. 처리 버튼을 선택한다.

| 버튼 | 조건 | 저장 후 상태 |
|---|---|---|
| 검토 내용 저장 | 일부만 체크해도 가능, 메모 선택 | 검토 중 |
| 보완 요청 | 공백이 아닌 보완 사유 필수, 체크 완료 불필요 | 보완 요청 |
| 승인 | 세 항목 모두 체크, 메모 선택 | 승인 |

‘검토 시작’은 상태 변경을 저장하는 동작이다. 창을 닫아도 ‘검토 중’은 유지된다.
체크와 메모는 위 처리 버튼을 눌러야 저장한다. 저장 전 닫은 입력은 버리고, 다시 열면 마지막 저장본을 읽는다.
‘이어서 검토’로 체크와 메모를 불러올 수 있다.
보완 요청·승인 후에는 ‘검토 결과 보기’에서 저장된 결과를 읽는다. 결과 창의 체크는 읽기 전용이다.

예: 요청한 1~12월 중 12월 고지서가 없다면 확인을 모두 완료하지 않고 ‘12월 고지서를 추가해 주세요’라는 사유로 보완 요청한다.
이 ‘승인’은 담당자가 요청에 맞는 자료로 확인했다는 뜻이며 제품 인증 완료를 뜻하지 않는다.

## 4. 받은 자료를 다시 기록했을 때

‘받은 자료 보기·수정’에서 보완 자료 등을 저장하면 다음과 같이 처리한다.

- 받은 자료 저장에 성공한 다음 상태를 ‘제출됨’으로 바꾼다.
- 이전 체크·검토 메모·보완 요청 또는 승인 결과를 제거한다.
- 다시 ‘검토 시작’을 누르면 세 체크는 모두 해제되고 메모도 빈 상태로 시작한다.
- 같은 값을 다시 저장한 경우에도 검토를 초기화한다. 저장 전 입력창에서 이 동작을 안내한다.
- 취소하거나 저장에 실패하면 기존 검토 결과를 유지한다.

바뀐 자료를 예전 자료에 대한 승인만으로 사용하지 않게 하기 위한 규칙이다.
현재는 검토 결과 한 건만 보관하며 이전 검토 이력을 별도로 쌓지 않는다. 이력·라운드·여러 증빙은 후속 확장이다.

## 5. 저장 구조와 처리 규칙

기존 저장 키 `ecoable-lca-manager.requests.v1`과 내부 `version: 1`을 유지하고, 검토한 요청에 `review` 객체를 추가한다.
기존 ‘요청’·‘제출됨’ 기록과 삭제 목록은 그대로 읽으며 초기화하지 않는다.

```json
{
  "status": "보완 요청",
  "review": {
    "checks": { "period": false, "scope": true, "complete": false },
    "note": "12월 고지서를 추가해 주세요.",
    "startedAt": "2026-10-16T03:00:00.000Z",
    "updatedAt": "2026-10-16T03:05:00.000Z",
    "receiptUpdatedAt": "2026-10-16T02:00:00.000Z"
  }
}
```

위 예시는 추가 필드만 설명한다. 실제 요청의 ID·원래 요청·기한·근거·받은 자료도 유지한다.

- 프로젝트 ID와 요청 ID를 함께 확인한다. 삭제한 요청·다른 프로젝트·없는 요청·받은 자료가 없는 요청에는 검토를 저장하지 않는다.
- ‘요청’은 받은 자료와 검토가 없고, ‘제출됨’은 받은 자료만 있다. ‘검토 중’·‘보완 요청’·‘승인’에는 유효한 받은 자료와 검토가 함께 있어야 한다.
- 검토 시작은 ‘제출됨’에서만 가능하다. 이미 ‘검토 중’인 요청의 시작을 다시 호출해도 체크를 지우거나 중복 저장하지 않는다.
- 검토 결과 저장은 ‘검토 중’에서만 가능하다. 결정된 결과를 직접 덮어쓰지 않는다.
- 체크는 세 키의 참/거짓 값으로 저장한다. 메모·보완 사유는 앞뒤 공백을 제거하고 최대 1,000자로 제한한다.
- 검토의 `receiptUpdatedAt`은 해당 받은 자료의 `updatedAt`과 같아야 한다.
- 창을 연 뒤 다른 저장 객체가 자료나 검토를 바꾸면, 최신 검토 객체와 창을 열 때의 객체를 비교해 이전 화면의 결과로 덮어쓰지 않는다. 창을 다시 열도록 안내한다.
- 삭제·복원 시 받은 자료·검토 상태·체크·보완 사유를 함께 유지한다.
- 저장에 성공한 후에만 화면·상태를 바꾼다. 쓰기 실패는 기존 저장본과 입력을 유지한다.
- 잘못된 체크·상태·자료 연결·시각은 저장본 읽기 실패로 안내하며 자동 초기화·덮어쓰기를 하지 않는다.
- 브라우저 저장을 사용한다. 사용자 계정·검토자 신원 인증·여러 탭의 읽기와 쓰기 사이를 잠그는 트랜잭션은 제공하지 않는다. 오래된 검토 화면의 저장을 거부하는 검사가 동시 쓰기 잠금을 의미하지는 않는다.

## 6. 화면과 파일

검토 창은 요청 내용·받은 자료·현재 상태·체크·메모를 함께 보여준다.
카드에도 확인 개수, 검토 메모 또는 보완 사유, 기록 시각을 표시한다.
세 체크 미완료 승인이나 사유 없는 보완 요청은 오류를 표시하고 해당 입력으로 초점을 옮기도록 구현했다.
입력 문장은 `textContent`로 출력하며 숨긴 결과 처리 버튼은 동작 대상에서 제외한다.

| 파일 | 역할 |
|---|---|
| `web/js/review.js` | 세 항목·입력 규칙·저장본 검사 |
| `web/js/requests.js` | 검토 시작·저장·상태 전환·재기록 초기화·최신 기록 확인 |
| `web/js/views/review.js` | 체크·메모·결과 창과 카드 요약 |
| `web/js/views/requests.js` | 요청별 검토 버튼과 상태·결과 표시 |
| `web/js/views/received-data.js` | 상태별 안내, 자료 재저장 시 검토 초기화 안내 |
| `web/index.html`, `web/css/app.css` | 창 템플릿·상태 색·체크·버튼 배치 |
| `web/tests/review.test.cjs` | 상태 전환·검토 조건·재기록·실패·기존 기록 보호 |

## 7. 확인 결과와 제한

| 확인 | 결과 |
|---|---|
| 자동 검사 | 검토 10개 + 기존 요청/받은 자료 25개 + 사전 6개 + 단계 4개 = 45개 통과 |
| 검토 시작 | 받은 자료 있는 제출됨만 시작, 시작 재호출은 기존 체크 유지 |
| 중간 저장 | 일부 체크와 메모를 검토 중으로 저장하고 다시 읽음 |
| 승인 조건 | 세 항목 중 하나라도 미확인이거나 체크 형식이 틀리면 거부 |
| 보완 사유 | 공백 사유 거부, 부분 체크와 구체적 사유는 허용 |
| 자료 재기록 | 검토 중·보완 요청·승인에서 재저장 후 제출됨과 빈 체크로 복귀 |
| 오래된 화면 | 다른 저장 객체가 체크·메모·자료를 바꾼 뒤 이전 결과 저장 거부 |
| 보호 | 다른 프로젝트·없는 요청·삭제 요청·이미 결정된 결과 변경 거부 |
| 삭제·복원 | 승인과 체크를 함께 복원 |
| 실패·손상 | 시작·결과·재기록 쓰기 실패에서 기존 원문 유지, 손상된 검토 자동 덮어쓰기 없음 |
| HTML | ID 중복 없음, label·설명 ID·스크립트 파일 연결 정상 |
| 로컬 서버 | HTTP 200, 새 검토 템플릿 제공 확인 |

**검증 제한:** 이전 작업에서 브라우저 도구가 로컬 미리보기 접근을 보안 정책으로 차단했다.
차단을 우회해 화면을 조작하지 않았다. 이번 검토 기능은 실제 브라우저 버튼 조작·초점 이동·작은 화면·캡처 검증을 완료했다고 설명하지 않는다.
동작 규칙 자동 검사와 HTML 검사 결과를 실제 화면 확인과 구분한다.

수동 확인 순서: 새로고침 → 제출됨 요청의 검토 시작 → 미체크 승인 차단 → 부분 체크·사유로 보완 요청 → 새로고침 후 사유 확인 → 받은 자료 재저장 → 빈 체크로 검토 시작 → 세 항목 체크 후 승인.

```bash
node --test web/tests/requests.test.cjs web/tests/review.test.cjs web/tests/glossary.test.cjs web/tests/stage-filter.test.cjs
```

## 8. 면접에서 설명하기

**무엇을 검토하나요?**

담당자가 회사에서 받은 자료를 보고 요청한 기간·제품과 사업장·필요한 항목과 증빙이 맞는지 확인합니다.
프로그램은 그 판단과 보완 사유를 기록합니다. 파일 내용 자동 검사나 제품 인증 심사는 아닙니다.

**왜 자료를 받았는데도 바로 승인하지 않나요?**

자료가 도착해도 요청한 달이 빠졌거나 다른 공장의 자료일 수 있습니다. 제출됨과 검토·승인을 구분했습니다.

**보완 자료가 왔는데 이전 체크를 왜 지우나요?**

이전 승인은 이전 자료에 대한 판단이므로 바뀐 자료에는 다시 확인이 필요합니다.
자료 재저장 후 제출됨으로 돌리고 체크와 결과를 초기화했습니다.

**다른 창에서 내용이 바뀌면 어떻게 하나요?**

검토 창을 열 때의 기록과 저장 직전 최신 기록을 비교합니다. 다르면 이전 화면의 판단을 저장하지 않고 다시 열도록 안내합니다.

## 9. 이번 범위 밖

해당 없음 상태, 검토자 계정, 검토 이력·라운드, 요청 원문 수정, 자동 누락 판정·실제 파일 연결,
AI 검토·자료 추출, 수집률·프로젝트 단계 자동 전환, 인증 완료 처리는 이번 기능에 포함하지 않는다.
다음 기능은 사용자의 화면 확인 후 함께 정한다.
