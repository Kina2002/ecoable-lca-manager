# WEB-016 D-day 두 종류와 업무 상태 용어 통일

## 1. 최종 합의

사용자는 프로젝트 목록에 D-day 두 종류를 보여주길 원했고, 기한 경과와 실제 완료를 구분하기로 했다. 최종 합의는 **날짜는 계속 세며 상태 딱지를 함께 표시하고, 실제 승인·완료일 때 멈추는 방식**이다.

- 마감일: 약속한 날짜다. 상태 이름으로 ‘마감’을 새로 만들지 않는다.
- 제출됨: 고객이 자료를 보냈다.
- 검토 중: 담당자가 확인 중이다.
- 보완 요청: 다시 받거나 고칠 부분이 있다.
- 승인: 자료를 검토해 사용할 수 있다고 판단했다.
- 완료: 프로젝트 전체 업무가 끝났다. 기존 마지막 단계 ‘완료·사후관리’와 연결한다.

F-05 기한 관리의 표시 부분과 사용자 추가 요구다. 알림 발송·메일 분류·오늘 할 일·완료 단계 전환까지 전체 구현한 것은 아니다.

## 2. 표시 위치

| 위치 | 표시 |
|---|---|
| 프로젝트 표 마지막 칸 | 프로젝트 목표 D-day와 목표일 + 자료 현황 D-day·대표 상태·승인 건수 |
| 프로젝트 상세 목표일 | 목표일과 프로젝트 D-day |
| 각 자료 요청의 제출 기한 | 제출 기한과 자료별 D-day, 기존 요청 상태 딱지 유지 |
| 데이터 수집 단계 자료 현황 | 각 요청의 제출 기한과 D-day·상태 |

표 마지막 칸 제목을 ‘일정 · 자료 현황’으로 바꾼다. 검색·단계·자료 필터의 의미나 프로젝트·자료 상태를 변경하지 않는다.

## 3. 날짜 규칙

1. 하루 전은 `D-1`, 당일은 `D-0`, 하루 지난 미완료는 `D+1`이다.
2. 프로젝트는 단계 10일 때만 **완료**로 고정한다. 기한 경과로 자동 완료하지 않는다.
3. 개별 자료는 요청·제출됨·검토 중·보완 요청에서 날짜를 계속 센다. **승인**이 되면 D-day 대신 승인으로 고정한다.
4. 제출됨·검토 중의 D+는 파란 계열로 표시한다. 기한이 지났다는 뜻이며 고객의 제출 지연이나 자료 누락을 자동 판정하지 않는다.
5. 요청·보완 요청은 경과일을 붉은 계열로, 0~3일 남은 경우 임박색으로 표시한다. 색 외에도 D-day와 상태 글자를 함께 표시한다.
6. 실제 달력 날짜를 검증하고 로컬 오늘 날짜의 연·월·일로 일수를 계산한다. UTC의 자정 날짜 번호로 비교해 시각·일광절약시간의 영향을 피하고 1~99년도 올바르게 처리한다.
7. 잘못된 날짜는 ‘기한 확인 필요’로 표시한다. 자료 저장소 읽기 실패는 ‘자료 확인 필요’이며 완료나 0건 성공으로 감추지 않는다.

## 4. 전체 프로젝트의 자료 현황

- 현재 프로젝트의 삭제되지 않은 요청만 집계한다.
- 자료가 하나도 없으면 **요청 없음**이다. 빈 요청 목록을 검토 완료로 판정하지 않는다.
- 요청이 있고 전부 승인됐으면 **자료 검토 완료**로 고정한다. 프로젝트 전체 완료와는 별개다.
- 나머지는 **미승인 자료 중 가장 이른 제출 기한**을 대표로 표시하고 그 항목의 상태를 붙인다. 같은 날짜면 기존 등록 순서를 유지한다.
- ‘승인 1/3건 · DRQ-0002’처럼 승인 건수와 대표 요청 번호도 표시한다. 대표 기한·번호는 툴팁에서 확인할 수 있다.
- 제출됐어도 검토 전이면 대표 기한 후보에 포함한다. 가장 급한 미제출 자료 모아보기나 홈의 오늘 할 일은 이후 별도 기능이다.
- 재기록으로 승인 상태가 제출됨으로 돌아오거나 보완 요청으로 바뀌면 원래 요청 기한 기준 D-day를 다시 표시한다. 이번에 보완 제출 기한을 새로 생성하거나 재설정하지 않는다.
- 프로젝트가 완료 단계라도 자료 현황은 실제 요청 기록대로 별도 계산한다. 누락된 자료 기록을 임의로 모두 승인 처리하지 않는다.

## 5. 날짜 갱신과 저장

- 분마다, 브라우저 화면으로 돌아왔을 때, 페이지가 다시 표시될 때 오늘 날짜와 D-day 글자만 갱신한다.
- 폼·필터·요청 목록을 다시 만들지 않아 입력 중인 값과 초점을 유지한다. 실제 브라우저 확인은 아래 제한을 참고한다.
- 승인·완료·요청 없음은 고정 표시라 날짜가 지나도 D+로 돌아가지 않는다.
- 모든 계산은 조회 전용이다. 기존 네 저장 키(projects/researchers/scope/requests)의 내용을 변경하지 않는다.
- 기본 샘플 목표일은 기존 시연 방식대로 앱을 열 때 기준일에서 상대적으로 생성한다. 재로딩하면 샘플 일정은 새 기준으로 생성된다. 직접 등록한 목표일과 자료 요청 기한은 저장된 고정 날짜다. 자정 갱신 중에는 샘플을 다시 만들지 않는다.
- 프로젝트 완료 처리는 현재 이미 존재하는 10단계 샘플로 확인할 수 있다. 사용자 프로젝트의 3단계 이후 이동·완료 버튼은 아직 별도 미구현 영역이다.

## 6. 검증

- `node --test web/tests/*.test.cjs`: **131개 통과**, 기존 119개 + D-day 검사 12개다.
- D-1/D-0/D+1, 연말·월말·윤년·1~99년·날짜 경계, 잘못된 날짜, 단계 10만 완료, 모든 자료 상태, 검토 중 경과색, 대표 기한·상태·승인 건수, 0건/전부 승인/삭제/프로젝트 분리, 동률 순서·원본 보존, 다음 날 갱신을 확인했다.
- 실제 요청 저장소의 제출→검토→승인→재기록→보완→삭제·복원 후 집계를 통합 검사했다.
- JavaScript 구문·HTML 정적 연결·HTTP 응답·공백 오류를 확인한다.
- 이전 브라우저 보안 정책 차단을 우회하지 않았다. **실제 두 D-day 배치·색·자정 갱신·입력 유지·작은 화면은 미확인**이다. 사용자 화면 확인이 필요하다.

## 8. 파일과 면접 설명

- `deadlines.js`: 날짜 차이와 프로젝트·개별 요청·자료 요약의 종료 조건.
- `views/deadlines.js`: 공통 배지와 날짜 글자만 갱신하는 연결.
- `project-list.js`, `project-detail.js`, `requests.js`, `collection.js`: 각 위치에 배지 표시.
- `app.js`: 최신 요청 읽기와 날짜 갱신 주기.
