# WEB-009 자료 상태별 건수와 필터

- 합의: 선택한 프로젝트의 자료 요청을 전체·요청·제출됨·검토 중·보완 요청·승인별로 세고 골라 본다.
- 기준: WEB-005~008 자료 요청·받은 자료·검토 결과 조회 보완.
- 상태: 구현·자동 검사 51개 통과. 실제 브라우저 화면 조작은 이전 보안 정책 차단으로 확인 제한이 있다.
- 다음 작업: 범위 상태 구분. 이번 작업에 섞어서 구현하지 않는다.

## 1. 왜 만드는가

자료가 늘어나면 현재 검토할 것과 다시 받아야 할 것을 한눈에 찾기 어렵다.
요청 카드마다 상태를 읽는 대신 상태별 개수를 보고 해당 자료만 골라 보게 한다.
예: ‘보완 요청 2건’을 누르면 현재 프로젝트에서 보완이 필요한 두 요청만 표시한다.
이는 목록 조회이며 자료 상태나 프로젝트 단계를 바꾸는 버튼이 아니다.

## 2. 사용 흐름

1. 프로젝트 상세의 ‘자료 요청’ 탭을 연다. 처음에는 ‘전체’를 선택한다.
2. 목록 위에서 상태별 건수를 확인한다.
3. 원하는 상태를 누르면 해당 상태의 요청 카드만 표시한다.
4. ‘전체’를 누르면 현재 요청을 모두 다시 표시한다. 이미 고른 상태를 다시 눌러도 선택을 유지한다.

버튼은 전체·요청·제출됨·검토 중·보완 요청·승인 여섯 개다.
현재 미구현인 ‘해당 없음’은 추가하지 않는다.
0건 상태도 버튼을 남겨 두고, 선택하면 해당 상태의 자료가 없다고 안내한다.
다른 프로젝트를 열거나 새로고침하면 전체 보기로 시작한다. 같은 상세의 다른 탭·용어사전 왕복에서는 기존 패널과 필터 선택을 유지한다.

## 3. 건수 규칙

- 현재 프로젝트 ID가 같고 삭제되지 않은 유효 상태의 요청만 센다.
- 상태별 건수는 필터로 줄이기 전의 전체 현재 목록에서 계산한다.
- 상태별 다섯 건수의 합은 전체 건수와 같다.
- 탭과 목록 제목의 건수는 전체 현재 요청 수를 유지한다.
- 별도 안내에 ‘전체 4건 중 검토 중 2건 표시’처럼 선택한 상태와 표시 건수를 보여준다.
- 삭제한 요청은 현재 건수·필터에서 제외한다. 기존 ‘삭제한 자료 요청’ 목록은 상태 필터와 별개로 유지한다.
- 선택된 상태로 조회해도 등록한 구분의 중복 방지는 전체 현재 목록을 기준으로 유지한다.
- 다른 프로젝트의 요청과 프로젝트 단계 정보는 변경하지 않는다.

## 4. 목록에서 상태를 바꿨을 때

등록·받은 자료 저장·검토 시작·중간 저장·보완 요청·승인·삭제·복원 후에 최신 저장 목록으로 건수를 다시 계산한다.
필터 선택은 같은 상세 안에서 유지한다.

예를 들어 ‘제출됨’을 보고 있을 때 검토를 시작하면 해당 요청은 ‘검토 중’이 되어 제출됨 목록에서 빠진다.
기록이 삭제된 것으로 오해하지 않도록 ‘전체 또는 검토 중에서 확인할 수 있다’고 안내한다.
승인 상태에서 받은 자료를 다시 저장하면 같은 방식으로 제출됨 건수가 늘고 승인 목록에서 빠진다.

바뀐 요청의 버튼이 여전히 보이면 그 버튼으로 초점을 돌리고, 목록에서 빠졌다면 선택 중인 상태 버튼으로 초점을 돌리도록 구현했다.
삭제 후에는 기존처럼 목록 제목으로 초점을 옮긴다.
필터 버튼 자체는 다시 만들지 않고 건수와 선택 표시를 갱신한다.

## 5. 저장·실패·접근성

- 필터는 화면에서 조회하는 정보다. 선택과 건수는 브라우저 저장본에 쓰지 않는다.
- 조회 함수는 원본 배열·자료 상태·단계를 변경하지 않고 새 목록을 만든다.
- 기존 자료 저장 키와 형식은 그대로다.
- 저장본을 읽지 못하면 건수를 0으로 속여 표시하지 않고 기존 오류를 안내하며 필터 영역을 숨긴다.
- 버튼의 `aria-pressed`로 선택 상태를, 이름으로 상태와 건수를 제공하고 `aria-controls`로 현재 목록을 연결한다.
- 결과 안내는 상태 영역으로 알린다. 버튼은 기본 키보드 Tab·Enter·Space 동작을 사용한다.
- 버튼은 줄바꿈되도록 배치한다. 실제 작은 화면 검증은 아래 제한에 해당한다.

## 6. 변경 파일

| 파일 | 역할 |
|---|---|
| `web/js/request-filter.js` | 프로젝트·삭제 여부·상태별 건수와 표시 목록을 계산 |
| `web/js/views/requests.js` | 버튼·선택·건수·빈 목록·상태 변경 안내·초점 연결 |
| `web/index.html` | 필터와 안내 영역, 신규 스크립트 연결 |
| `web/css/app.css` | 필터 버튼·선택 표시·줄바꿈 |
| `web/tests/request-filter.test.cjs` | 순수 조회와 기존 실제 저장 규칙을 연결해 검사 |

저장된 현재 요청 읽기 → 프로젝트의 전체 건수 계산 → 선택 상태의 카드만 표시 순서다.
전체 집계와 필터 결과를 분리해, 필터를 눌렀다고 다른 상태의 건수가 사라지지 않게 했다.

## 7. 확인 결과와 제한

| 확인 | 결과 |
|---|---|
| 자동 검사 | 필터 6개 + 기존 45개 = 51개 통과 |
| 범위 | 다른 프로젝트와 삭제된 요청을 집계에서 제외 |
| 집계 | 상태별 합계가 전체와 같고, 필터 선택 후에도 전체 건수 유지 |
| 순서·보존 | 원래 요청 순서로 조회, 원본 배열·상태·프로젝트 단계 유지 |
| 빈 목록 | 0건 상태·빈 프로젝트·전체 보기 처리 |
| 저장 연계 | 실제 저장 코드로 제출·검토·보완·승인·재기록 후 건수와 표시 목록 확인 |
| 삭제·복원 | 실제 저장 코드에서 삭제 제외와 복원 후 건수 확인 |
| 읽기 전용 | 모든 필터로 조회해도 저장본과 쓰기 횟수 유지 |
| 문법·연결 | 변경 JS 2개 문법, HTML ID·label·설명·스크립트 경로 정상 |
| 로컬 서버 | HTTP 200, 새 필터 템플릿 제공 확인 |

검사 명령:

```bash
node --check web/js/request-filter.js
node --check web/js/views/requests.js
node --test web/tests/request-filter.test.cjs web/tests/requests.test.cjs web/tests/review.test.cjs web/tests/glossary.test.cjs web/tests/stage-filter.test.cjs
```

이전 브라우저 도구의 미리보기 접근 차단을 우회하지 않았다.
실제 화면에서 필터 버튼·상태 변경 후 초점·용어사전 왕복·작은 화면을 조작한 검증은 미완료다.
위 결과는 코드 자동 검사이며 실제 브라우저 동작 확인으로 설명하지 않는다.

수동 확인: 새로고침 → 자료 요청 탭 → 상태별 건수 확인 → 상태 선택 → 0건 안내 → 전체 보기 → 제출됨에서 검토 시작 → 변경된 건수와 안내 확인.

## 8. 면접에서 설명하기

**왜 필터가 필요한가요?**

요청이 많아지면 보완할 자료나 검토할 자료를 찾기 어렵습니다. 현재 프로젝트의 요청을 상태별 건수와 필터로 빠르게 찾게 했습니다.

**필터를 누르면 업무 단계가 넘어가나요?**

해당 상태의 자료만 조회합니다. 개별 자료 상태와 프로젝트 전체 단계는 별도 정보이며 필터는 둘 다 변경하지 않습니다.

**상태를 바꾸고 목록에서 사라지면 어떻게 알 수 있나요?**

현재 필터와 다른 상태가 되어 숨겨졌다고 안내하고, 전체나 새 상태에서 확인할 수 있게 합니다. 건수도 전체 저장 기록을 기준으로 다시 계산합니다.

## 9. 다음 순서에 대한 사용자 결정

사용자는 이 필터를 먼저 만들고 **범위의 미정·고객 요청안·협의 중·확정 표시를 그다음에 넣자**고 했다.
현재 가상 샘플이 계약·범위 정의 단계에서도 경계 값을 확정된 것처럼 보여 혼동된다는 문제를 기록했다.
범위 상태는 바로 다음 작업이며 이번 코드에서는 범위 표시나 프로젝트 단계를 변경하지 않았다.

업무 흐름은 범위를 합의하고 필수 정보가 갖춰지면 데이터 수집으로 진행하는 것이다.
시스템 경계의 ‘확정’ 값 하나만으로 자동 단계 전환을 약속하지 않는다.
기준량·시스템 경계·기준기간·적용 기준 등 전환 조건과 실제 단계 이동 방식은 해당 작업에서 함께 정한다.
