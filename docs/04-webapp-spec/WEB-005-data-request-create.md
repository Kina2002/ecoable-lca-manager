# WEB-005 프로젝트별 자료 요청 등록과 저장

- 기준: 설계서 v02 F-03·F-10, DataRequest 엔터티.
- 합의: 자료 요청 탭에서 구분 하나를 선택하고 기본 문장을 수정해 제출 기한과 등록한다. 근거를 자동 표시하며 '요청' 상태로 저장하고 새로고침 후 복원한다.
- 범위: F-03의 개별 등록·중복 방지·근거 표시, F-10의 요청 기록 브라우저 저장 부분.
- 상태: 구현·검증 완료. 코드와 이 문서를 같은 커밋으로 관리한다.

## 1. 왜 만드는가

컨설팅 담당자는 고객사의 제품을 평가할 때 필요한 자료를 모아야 한다.
이 기능은 프로젝트별로 '어떤 자료를 언제까지 받아야 하는지' 적는 체크리스트다.
실제 사용량·배출량 입력 전, 받을 자료의 목록부터 정리한다.

예: 라온소재의 양극재 전구체 평가에서 지난해 전력 사용량과 고지서를 받아야 한다.
에너지 구분으로 요청 내용과 기한을 기록하면, 다른 회사의 업무와 섞이지 않고 다시 확인할 수 있다.
등록은 요청 내용을 앱에 기록하는 행위다. 외부로 메일이나 알림을 발송하지 않는다.

## 2. 화면과 사용 흐름

1. 프로젝트 번호를 눌러 상세를 연다.
2. '개요·범위' 옆의 '자료 요청' 탭을 선택한다. 탭 숫자는 그 프로젝트에 등록한 요청 수다.
3. 11가지 중 자료 구분 하나를 고른다. 필요한 항목은 프로젝트 범위에 따라 담당자가 선택한다.
4. 자동으로 나온 기본 요청 문장을 읽고, 필요한 기간·자료·증빙을 구체적으로 적는다.
5. 구분에 연결된 지침의 참고 근거와 원문 페이지를 확인한다.
6. 제출 기한을 골라 '자료 요청 등록'을 누른다.
7. 저장에 성공하면 자동 번호·자료 구분·내용·제출 기한·'요청' 상태가 목록에 표시된다.
8. 새로고침한 뒤 같은 프로젝트의 자료 요청 탭을 열면 저장한 목록이 복원된다.

등록 후 구분·문장은 비우고 제출 기한은 유지해 다음 항목을 이어 적기 쉽게 했다.
이미 등록한 구분은 선택 목록에 '등록됨'으로 표시하고 비활성화한다.

## 3. 입력 정보와 뜻

| 항목 | 입력/자동 | 의미 |
|---|---|---|
| 프로젝트 | 상세에서 자동 연결 | 어느 업무에 필요한 자료인지 |
| 자료 구분 | 필수 선택 | 비슷한 자료를 묶는 이름표. 에너지·운송 등 11개 |
| 요청 내용 | 필수, 1,000자 이내 | 그 프로젝트에서 실제로 받고 싶은 자료·기간·증빙. 앞뒤 공백 제거 |
| 제출 기한 | 필수 날짜 | 고객사에서 자료를 받기로 한 날 |
| 요청 번호 | 자동 | 브라우저 저장본 전체에서 DRQ-0001부터 증가 |
| 상태 | 자동 '요청' | 필요한 자료로 등록한 상태. 실제 메일 발송 여부를 의미하지 않음 |
| 지침 근거 | 구분별 자동 | 자료 준비에 참고할 관련 부분, 출처·확인일·페이지 |
| 등록 시각 | 자동 저장 | 기록을 만든 시각. 현재 화면에는 별도 표시하지 않음 |

같은 구분의 여러 자료는 한 요청 내용에 함께 적는다. 프로젝트별 같은 구분은 한 번만 등록한다.
예를 들어 에너지 요청에 월별 전력, 연료 사용량, 각 증빙을 함께 적을 수 있다.
다른 프로젝트에는 같은 구분을 별도로 등록할 수 있다.

## 4. 확인과 예외 규칙

- 미선택·공백뿐인 내용·빈 날짜·존재하지 않는 날짜는 등록하지 않는다. 첫 오류 입력칸으로 초점을 옮기고 이유를 표시한다.
- 사용자가 값을 고치면 해당 칸의 이전 오류 문구를 지운다. 등록 시 전체를 다시 검증한다.
- 윤년과 월별 일수를 확인한다. 예: 2024-02-29는 가능, 2026-02-29는 불가.
- 과거 기한도 기록할 수 있다. 기한 초과·D-3 등 판단과 경고는 별도 F-05 기능에서 구현한다.
- 화면에서 비활성화한 중복 구분을 저장 규칙에서도 검사해 중복 기록을 막는다.
- 유효한 프로젝트 ID에만 연결한다. 이름이나 화면의 행 위치로 연결하지 않는다.
- 구분을 잠시 바꿨다가 돌아오면 해당 구분에서 수정하던 문장을 복원한다. 이 임시 문장은 현재 열린 상세 화면 안에서만 유지한다.
- 사전을 열었다 돌아오면 선택 탭·작성 중 입력·저장 목록이 유지된다.
- 목록으로 나갔다 상세를 다시 열거나 새로고침하면 작성 중 입력은 초기화하고 저장한 기록을 읽는다. 상세는 개요·범위 탭에서 시작한다.
- 화면에 데이터 문장은 `textContent`로 넣어 HTML로 실행하지 않는다.
- 탭은 클릭·Enter·Space와 좌우 화살표·Home·End를 지원한다. 선택 탭 하나만 Tab 이동 순서에 넣는다.
- 저장 성공은 상태 영역으로 안내한다. 실패하면 성공 문구나 새 카드를 표시하지 않고 입력을 남긴다.

## 5. 브라우저 저장

저장 키: `ecoable-lca-manager.requests.v1`.

```json
{
  "version": 1,
  "nextNumber": 2,
  "requests": [
    {
      "id": "DRQ-0001",
      "projectId": "project-001",
      "categoryKey": "energy",
      "detail": "2025년 전력 사용량과 고지서",
      "dueDate": "2026-10-23",
      "status": "요청",
      "createdAt": "등록 시각",
      "guideline": "등록 당시 근거 객체"
    }
  ]
}
```

위 예시는 구조 설명용이다. 실제 `createdAt`은 ISO 시각 문자열이고 `guideline`은 출처·구간·페이지·URL·확인일·안내 문장을 담는 객체다.

- 저장본이 없으면 빈 목록으로 시작한다. 읽기만 했다고 저장본을 만들지 않는다.
- 매번 최신 저장본을 읽어 기존 다른 프로젝트의 요청과 일련번호를 이어 쓴다.
- `setItem`에 성공한 다음에만 새 기록을 성공으로 반환한다.
- 저장소 접근 차단·공간 부족·쓰기 오류는 잡아서 안내한다. 입력은 유지한다.
- 깨진 JSON·지원하지 않는 버전·잘못된 날짜·중복·알 수 없는 프로젝트 등은 읽기 실패로 처리한다. 기존 값을 덮어쓰거나 자동 삭제하지 않는다.
- 잘못된 근거 URL도 거부한다. 근거 링크는 확인한 법령정보센터 첨부 URL을 사용한다.
- 프로젝트 샘플은 기존처럼 실행일을 기준으로 생성한다. 사용자 요청 기록과 기한은 별도 저장하므로 새로고침 때 새 날짜로 바뀌지 않는다.
- 저장은 같은 브라우저·같은 사이트 주소에 속한다. 서버 계정이나 여러 사용자 간 동기화 기능은 없다. 여러 탭에서 동시 등록하는 상황을 위한 트랜잭션 잠금은 구현하지 않았다.
- 저장 키의 버전과 내부 `version`을 두어 이후 구조를 바꿀 때 구분할 수 있다. 내보내기·가져오기·초기화·마이그레이션 화면은 이번 범위가 아니다.

링크는 관련 내용이 시작하는 PDF 페이지를 연다. 복수 구간은 본문을 함께 확인한다.
근거 객체를 등록 시점의 기록에 함께 저장해 이후 기본 안내가 바뀌어도 원래 참고한 내용을 남긴다.

시연 확인을 위해 현재 로컬 브라우저의 라온소재에 에너지 요청 한 건을 남겼다.
내용은 '2025년 1월~12월 공정별 전력 사용량(kWh)과 월별 전기요금 고지서', 기한은 2026-10-23이다.
이 브라우저의 가상 시연 기록이며 GitHub 소스에 저장한 실제 고객 기록이 아니다.

```bash
node --test web/tests/requests.test.cjs web/tests/glossary.test.cjs web/tests/stage-filter.test.cjs
```

## 9. 면접에서 설명하기

**어떤 문제를 해결했나요?**

여러 고객사의 평가에 필요한 자료를 기억에 의존하면 누락되거나 다른 업무와 혼동될 수 있습니다.
프로젝트별로 자료 구분·요청 내용·기한을 등록하는 체크리스트를 만들었습니다.

**구분과 요청 내용은 어떻게 다른가요?**

구분은 에너지 같은 분류 이름이고, 내용은 해당 프로젝트에서 원하는 기간·자료·증빙을 구체적으로 적은 문장입니다.
기본 문장을 제공하되 수정할 수 있게 했습니다.

**어느 프로젝트의 자료인지 어떻게 구분하나요?**

각 요청에 고유한 프로젝트 ID를 저장하고, 목록에서는 같은 ID의 요청만 골라 보여줍니다.

**새로고침해도 왜 남아 있나요?**

요청 명단을 JSON 문자열로 바꿔 브라우저 localStorage에 저장하고, 상세를 열 때 다시 읽습니다.
저장 실패·잘못된 형식도 처리해서 저장되지 않은 항목을 성공했다고 보여주거나 기존 기록을 덮어쓰지 않게 했습니다.

**왜 근거를 함께 표시하나요?**

자료를 왜 받아야 하는지 참고할 수 있게 하기 위해서입니다. 확인한 작성지침의 관련 부분을 구분별로 연결했습니다.
프로젝트마다 적용 기준이 다르므로 자동 의무 판정과 구분해 참고 근거라고 표시합니다.

## 10. 이번 기능의 경계

전체 F-03의 일괄 생성·프로젝트 단계 자동 전환은 포함하지 않는다. 이번에 합의한 것은 한 항목 등록부터다.
현재 프로젝트 단계와 위쪽 단계별 집계는 자료 요청을 등록해도 바꾸지 않는다.
요청 수정·삭제, 제공 부서·대상 제품 지정, 제출 값·증빙 파일명·1차/2차·계수 데이터셋 입력, 상태 변경은 이후 별도로 구현한다.
메일 발송·메일 초안·기한 경고·수집률·인증 관리·실제 공개 데이터 표본 적용도 이번 범위가 아니다.
기존 `constants.js`, `rules.js`의 모든 v02 요구를 완성했다고 표시하지 않는다.
다음 기능은 사용자가 화면과 설명을 확인한 뒤 함께 정한다.
