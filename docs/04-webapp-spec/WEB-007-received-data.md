# WEB-007 받은 자료 기록하기

- 기준: 설계서 v02 F-04의 첫 부분, DataRequest 엔터티.
- 합의: 요청별 제출 값·단위·자료 기간·증빙 파일 이름을 저장하고 상태를 ‘요청’에서 ‘제출됨’으로 변경한다.
- 완료 범위: 받은 자료 기록·확인·수정, 수치/문서 형태, 입력 검증, 브라우저 저장과 새로고침 복원.
- 확인일: 2026-10-16. 자동 검사 35개 통과. 실제 화면에서 저장·수정·취소·새로고침·프로젝트 분리를 확인했다. 추가 화면 확인 제한은 7절에 기록한다.

## 1. 왜 만드는가

WEB-005의 요청은 ‘무슨 자료를 언제까지 받아야 하는지’ 적는 목록이다.
이번에는 자료가 도착한 뒤 ‘실제로 받은 값과 근거’를 해당 요청에 연결한다.
담당자가 메일·엑셀 등으로 받은 자료를 보고 앱에 기록하는 흐름이다.

예를 들어 전력 사용량 12,000만 적으면 단위와 기간을 알 수 없다.
12,000 kWh, 2025-01-01~2025-12-31, 해당 고지서 파일 이름을 함께 보관하면 무엇을 받은 것인지 다시 확인할 수 있다.
사업장 주소·제품 사양처럼 숫자 한 개로 나타낼 수 없는 자료에는 문서 설명을 기록한다.

‘제출됨’은 자료를 받았다는 뜻이다. 검토해서 사용할 수 있다고 판정하는 ‘승인’과 구분한다.

## 2. 사용 흐름

1. 프로젝트 상세 → ‘자료 요청’ 탭에서 요청의 ‘받은 자료 기록’을 누른다.
2. 입력창 위에서 요청 번호·자료 구분·요청 내용을 확인한다.
3. 자료 형태를 선택한다. 수치 자료는 제출 값·단위, 문서 자료는 받은 내용을 적는다.
4. 자료 기간 시작일·종료일과 증빙 파일 이름을 적는다.
5. ‘받은 자료 저장’을 누른다.
6. 입력 검증과 브라우저 저장에 성공하면 창을 닫고, 요청 상태와 카드에 ‘제출됨’·받은 내용·기간·증빙을 표시한다.
7. ‘받은 자료 보기·수정’에서 저장한 값을 다시 읽고 고칠 수 있다.

취소·닫기는 입력을 저장하지 않는다. 다시 열면 마지막 저장본으로 시작한다.
새 요청이나 새 요청 번호를 만드는 것이 아니므로, 받은 자료를 저장해도 요청 건수와 제출 기한은 그대로다.
프로젝트 단계도 그대로 유지한다.

## 3. 입력 항목

| 항목 | 입력 규칙 | 목적 |
|---|---|---|
| 자료 형태 | 수치 자료 / 문서·설명 자료 | 받은 자료에 맞는 입력칸 선택 |
| 제출 값 | 수치 자료 필수, 0 이상 숫자 | 사용량·중량 등 원자료의 값 |
| 단위 | 수치 자료 필수, 14개 선택지 | kg·kWh 등 숫자의 의미 |
| 밀도 | m³·L일 때 필수, 0보다 큰 수, kg/m³ | 부피를 질량으로 해석할 때 필요한 근거 |
| 받은 내용 | 문서 자료 필수, 1~1,000자 | 주소·사양·설명 등 받은 내용 요약 |
| 자료 기간 | 시작일·종료일 필수, 실제 날짜 | 어느 기간의 자료인지 구분 |
| 증빙 파일 이름 | 필수, 1~200자, 폴더 경로 제외 | 원본 자료를 다시 찾기 위한 이름 |

단위: kg, g, t, kWh, MJ, GJ, m³, L, tkm, km, 개, 장, kgCO₂e, %.
구분에 기본 단위가 있으면 처음 열 때 제안하지만, 담당자가 원자료에 맞게 바꿀 수 있다.
일반정보·사용/폐기 단계처럼 기본 단위가 없는 구분은 문서 형태로 시작하며 수치 형태로 바꿀 수도 있다.

숫자는 쉼표와 소수점을 허용한다. 예: `12,000.50` → 저장값 `12000.50` → 표시 `12,000.50`.
소수 부분을 화면에서 임의 반올림하지 않는다. 숫자는 문자열로 보관하고 계산은 하지 않는다.
음수·지수 표기·문자·잘못된 쉼표·안전한 숫자 범위를 넘는 값은 거부한다. 0은 실제 받은 값으로 허용한다.
입력 길이는 숫자당 최대 50자이며 숫자 크기는 JavaScript의 `Number.MAX_SAFE_INTEGER` 이하다.

자료 기간은 요청 기한과 다른 정보다. 기한은 ‘언제까지 받을지’, 자료 기간은 ‘어느 기간의 값인지’다.
새 날짜 입력도 연도 4자리·숫자 8자리 입력·달력 선택을 재사용한다.
종료일은 시작일과 같거나 이후여야 한다. 과거 기간과 같은 날의 시작/종료도 허용한다.

밀도는 설계서의 부피 단위 규칙에 따라 함께 기록하며 자동 환산은 하지 않는다.
파일은 이름만 기록한다. 파일 업로드·열기·실제 내용 검증은 이번 기능에 포함하지 않는다.

## 4. 저장과 상태

저장 키와 버전은 기존 `ecoable-lca-manager.requests.v1`, `version: 1`을 유지한다.
기존 ‘요청’ 기록과 삭제 기록을 초기화하지 않고, 해당 요청에 `receipt` 객체를 추가한다.

```json
{
  "id": "DRQ-0001",
  "projectId": "project-001",
  "status": "제출됨",
  "receipt": {
    "kind": "quantity",
    "value": "12000",
    "unit": "kWh",
    "density": "",
    "description": "",
    "periodStart": "2025-01-01",
    "periodEnd": "2025-12-31",
    "evidenceFileName": "가상_2025년_전기요금고지서.xlsx",
    "recordedAt": "2026-10-16T03:00:00.000Z",
    "updatedAt": "2026-10-16T03:00:00.000Z"
  }
}
```

위 예시는 추가 필드 설명용이다. 실제 요청에는 기존 내용·기한·등록 시각·지침 근거도 남는다.
`recordedAt`은 앱에 최초 기록한 시각이며 실제 고객의 발송·수신 시각을 뜻하지 않는다.
수정할 때 최초 기록 시각은 유지하고 `updatedAt`을 갱신한다.

- 현재 요청 중 프로젝트 ID와 요청 ID가 모두 일치하는 요청에만 저장한다.
- 삭제한 요청·다른 프로젝트·없는 번호에는 기록하지 않는다.
- 수치/문서 형태에 따라 필요 없는 필드는 빈 문자열로 보관한다. 숨긴 이전 입력을 다른 형태의 자료에 섞지 않는다.
- ‘요청’ 상태에는 받은 자료 객체가 없고, ‘제출됨’ 상태에는 유효한 받은 자료 객체가 있어야 한다.
- 삭제·복원할 때 받은 내용과 ‘제출됨’ 상태도 보존한다.
- 매번 최신 저장본을 읽고 선택한 요청만 바꾼다. 다른 프로젝트의 기록·요청 번호는 유지한다.
- 저장 실패에서는 창과 입력을 남기고 성공 안내·상태 변경을 하지 않는다.
- 손상된 저장본·알 수 없는 상태·잘못된 받은 자료는 오류로 안내하고 기존 원문을 덮어쓰지 않는다.
- 같은 브라우저·사이트 주소에 보관한다. 서버 동기화와 여러 탭의 동시 쓰기 잠금은 기존처럼 제공하지 않는다.

현재는 요청 한 건당 받은 자료의 현재 기록 한 건을 보관한다.
여러 수치 행·여러 파일·변경 이력은 별도 확장 범위다. 같은 기록을 수정하면 이전 값 대신 새 값을 저장한다.

## 5. 화면과 접근성

- 요청 카드의 버튼으로 여는 기본 HTML `dialog`를 사용한다.
- 각 입력에 이름·필수 안내·오류 설명을 연결한다. 저장 시 첫 오류 칸으로 초점을 옮긴다.
- 자료 형태와 단위에 따라 사용하지 않는 입력을 숨기고 비활성화한다.
- 취소·닫기 후에는 열었던 버튼으로, 저장 후에는 갱신된 요청의 확인·수정 버튼으로 초점을 돌린다.
- 결과는 기존 상태 안내 영역으로 알린다.
- 문서 설명과 파일 이름은 `textContent`로 출력한다.
- 좁은 화면에서는 값/단위와 시작/종료 날짜를 한 열로 배치한다. 창 높이는 화면에 맞게 제한하고 내부를 스크롤한다.

실제 파일과 고객 데이터가 아니며 GitHub 소스에 해당 브라우저 기록을 포함하지 않는다.
기존 삭제 목록과 다른 프로젝트 기록은 초기화하지 않았다.

작업 재개 후 브라우저 도구가 미리보기 접근을 보안 정책으로 차단하여 추가 조작을 중단했다.
새 기능의 작은 화면 배치·기간 달력 선택·키보드 초점 제한은 추가 수동 확인이 필요하다.
반응형 CSS 구현과 위 DOM 치수 확인을 실제 휴대폰의 시각 검증으로 설명하지 않는다.

## 8. 면접에서 설명하기

**이 기능을 왜 만들었나요?**

요청 목록만 있으면 자료가 실제 도착했는지, 어떤 값과 근거를 받았는지 알기 어렵습니다.
기존 요청에 받은 내용과 근거 파일 이름을 연결해 기록하고 ‘제출됨’으로 표시했습니다.

**왜 단위와 기간도 기록하나요?**

같은 12,000이라도 kg인지 kWh인지에 따라 의미가 다르고, 한 달 사용량과 1년 사용량도 다릅니다.
담당자가 숫자를 다시 이해할 수 있도록 값과 단위·기간을 함께 보관했습니다.

**제출됨과 승인은 어떻게 다른가요?**

제출됨은 자료를 받았다는 뜻이고, 승인은 검토 후 사용할 수 있다고 판단한 상태입니다.
이번에는 자료를 받는 단계까지 구현했고 검토·승인은 다음 기능으로 나눴습니다.

**저장 실패는 어떻게 처리했나요?**

검증 후 브라우저 저장에 성공한 경우에만 상태와 화면을 바꿉니다.
실패하면 입력창을 유지하고, 기존 값과 상태를 보존합니다. 잘못된 저장본도 자동으로 덮어쓰지 않습니다.

## 9. 다음에 함께 구현할 범위

F-04 전체 완료가 아니다. 활동량/계수의 1차·2차 출처, 획득 방법, 계수 데이터셋 이름·버전·연도, 증빙 종류,
검토·보완 사유·승인·해당 없음, 여러 수치 행과 이력은 별도로 함께 정한다.
