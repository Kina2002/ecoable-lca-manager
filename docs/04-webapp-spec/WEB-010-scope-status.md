# WEB-010 범위 합의 상태와 데이터 수집 시작

- 기준: 설계서 v02 F-01 중 범위 정보·단계 이동의 일부, 기존 대화의 범위 상태 구분 요구.
- 사용자 확정: 미정 / 고객 요청안 / 협의 중 / 확정. **확정 저장 후 별도 ‘데이터 수집 시작’ 버튼으로 이동**한다.
- 2026-10-16 구현. 실제 회사 자료·합의 기록이 아닌 가상 시연 데이터다.

## 1. 왜 만드는가

계약 단계에 ‘요람~문’이 적혀 있어도 고객이 희망한 안인지 양쪽이 합의한 안인지 알 수 없었다. 평가 범위의 **내용**과 그 내용의 **합의 상태**를 분리한다.

예: ‘제품 1장 · 요람~무덤’ + ‘협의 중’은 검토 중인 안이고, 같은 내용 + ‘확정’은 합의가 끝났다고 사용자가 기록한 안이다. 앱이 기준 적합성을 심사하거나 고객 동의를 직접 확인하는 것은 아니다.

| 상태 | 앱에서의 의미 |
|---|---|
| 미정 | 아직 평가 범위를 정하지 않음 |
| 고객 요청안 | 고객이 원하는 범위를 제시함 |
| 협의 중 | 요구·적용 기준·자료 확보 가능성을 함께 확인하는 중 |
| 확정 | 이 범위로 진행하기로 합의했다고 사용자가 기록함 |

네 상태를 반드시 순서대로 거치도록 강제하지 않는다. 계약 단계에서도 이미 고객 요청안이나 확정안이 있을 수 있다. 프로젝트 단계로 범위 상태를 자동 추론하지 않는다.

## 2. 이번 구현 범위

1. 프로젝트 목록과 개요·범위에 합의 상태를 표시한다.
2. 계약·착수(1), 범위 정의(2) 단계 상세의 ‘범위 합의 기록’에서 상태·기준량·단위·경계·기준기간·적용 기준·비12개월 사유를 저장한다.
3. 제품명은 기존 프로젝트 값을 표시하며 이 화면에서 변경하지 않는다.
4. 확정 저장은 현재 단계를 유지한다.
5. 범위 정의 단계에서 저장된 상태가 확정이고 필수 정보가 유효하면 ‘데이터 수집 시작’으로 **2 → 3**만 허용한다.
6. 목록·단계별 건수·수집 단계의 자료 현황에 새 단계를 반영한다. 기존 회사별 자료 상태 필터와 수집 단계 하위 필터는 유지한다.
7. 새로고침 후 같은 브라우저에서 범위·단계를 복원한다. 기존 요청·받은 자료·검토 저장소는 변경하지 않는다.

## 3. 저장과 시작 조건

- 미정·고객 요청안·협의 중은 빈 항목을 포함해 초안 저장 가능하다.
- 입력한 날짜는 실제 달력 날짜여야 하고 시작일 ≤ 종료일이어야 한다. 숫자 8자리 입력·연도 4자리와 기존 달력 보조를 사용한다.
- 입력한 기준량은 양의 일반 소수 또는 정수이며 지수 표기·0·음수는 거절한다. 비어 있는 초안은 허용한다.
- 확정은 대상 제품, 양의 기준량과 단위, 경계, 시작·종료일, 적용 기준 하나 이상이 필요하다.
- 이 기능은 기준기간 시작일의 다음 해 같은 날짜 직전일까지를 12개월로 본다. 그 외 기간을 확정하려면 사유를 기록한다. 기존 미연결 `rules.isTwelveMonths`의 360~370일 근사 규칙과 별개로 이번 저장 기능에서 명시적으로 검사한다.
- 상태나 필드를 변경하면 시작 버튼을 비활성화한다. 먼저 저장해야 하며 달력으로 바꾼 경우도 동일하다.
- 확정을 저장한 뒤 버튼으로 시작한다. 별도 확인 팝업은 추가하지 않는다.
- 1단계에서 범위 확정 저장은 가능하지만 수집 시작 버튼은 없다. 계약→범위 단계 이동은 별도 구현 대상이다.
- 3단계 이상은 읽기 전용이다. 수집 이후 재협의·변경 이력·되돌리기는 이후 함께 정한다.
- 이번 검사는 시연용 최소 준비 조건이다. 기타 경계의 상세 설명, 컷오프·할당·배경 DB, 세부 PCR 조건, 기능·수명 등 전체 범위 정의나 기준별 적합성 검증을 완료한 것이 아니다.

## 4. 가상 샘플

- 해든솔라: 범위 정의 / 협의 중. 이 프로젝트로 확정 저장→수집 시작을 체험한다.
- 이음모빌리티: 계약·착수 / 고객 요청안. 기준기간·적용 기준은 미정이다.
- 다른 다섯 프로젝트: 기존 후속 단계 / 확정으로 명시한다.
- 체험용 기준기간은 2025-01-01~2025-12-31, 적용 기준은 ISO 14040/44를 입력해 놓았다. 실제 제품·인증에 필요한 기준을 모두 판단한 목록이 아니다.
- 기존 샘플의 제품·경계·단계는 사용자가 이동하기 전까지 유지한다. 샘플 상태는 프로젝트 ID별 명시 값이다.

## 5. 저장·실패 처리

- 별도 키 `ecoable-lca-manager.scope.v1`, `{version:1,records:{프로젝트ID:범위와단계}}`.
- 최초 읽기는 쓰지 않는다. 기존 요청 키 `ecoable-lca-manager.requests.v1`과 분리한다.
- 저장 성공 후에만 메모리와 화면에 반영한다. 저장소 접근 거절·용량 부족 시 입력을 유지하고 단계도 바꾸지 않는다.
- JSON 손상·다른 버전·알 수 없는 프로젝트·잘못된 상태나 단계 전환은 읽기 실패로 처리하고 원본을 덮어쓰지 않는다. 화면 상단에도 최신 저장 상태를 확인하지 못했다고 표시한다.
- 화면을 열 때 읽은 범위와 저장 직전 최신 범위가 다르면 저장·시작을 거절한다. 목록으로 돌아가 재진입하도록 안내한다. 동시에 발생하는 쓰기에 대한 원자적 잠금이나 실시간 다중 사용자 동기화는 제공하지 않는다.
- 현재 브라우저 저장 방식이며 서버 DB·로그인·파일 업로드·실제 메일·AI를 연결하지 않는다.

## 6. 확인 절차

1. 새로고침하고 목록에서 해든솔라의 ‘범위: 협의 중’을 확인한다.
2. 해당 프로젝트 개요·범위 → 범위 합의 기록에서 확정을 선택하고 범위 저장한다.
3. 상태는 확정, 현재 단계는 여전히 범위 정의인지 확인한다.
4. 기준량·기준기간을 수정하면 수집 시작이 잠기는지 확인한다. 저장한 뒤 다시 활성화되는지 확인한다.
5. 데이터 수집 시작을 눌러 현재 단계가 데이터 수집으로 바뀌는지 확인한다.
6. 목록에서 범위 정의 건수 -1, 데이터 수집 건수 +1과 해당 필터 소속을 확인한다. 선택 중인 범위 정의 필터에선 해당 프로젝트가 사라지는 것이 정상이다.
7. 새로고침 후에도 이동한 단계·범위가 유지되는지 확인한다.
8. 기존 자료 요청·받은 자료·검토 기록과 회사별 상태 필터가 남아 있는지 확인한다.

## 7. 검증과 제한

- `node --test web/tests/*.test.cjs`: **70개 통과**. 새 범위 검사 13개와 기존 57개다.
- 새 검사는 명시 샘플·조회 무쓰기·네 상태·초안/확정 조건·유효 날짜·기간 사유·별도 단계 이동·재로딩·계약 단계 건너뛰기 방지·수집 후 변경 방지·저장 실패·손상 보존·다른 탭 변경 감지를 확인한다.
- 변경 JavaScript 구문, HTML ID/스크립트 경로, 공백 오류와 HTTP 응답을 확인한다.
- 이전 브라우저 접근이 보안 정책으로 차단되어 우회하지 않았다. **실제 화면 클릭·달력·작은 화면·초점 이동은 추가 확인이 필요하다.** 자동 검사 통과를 실제 UI 확인으로 설명하지 않는다.

## 8. 파일 역할과 면접 설명

- `web/js/scope.js`: 필수 정보·합의 상태·허용 단계 전환과 저장을 담당한다.
- `web/js/views/scope.js`: 입력칸과 두 버튼, 안내·오류 메시지를 만든다.
- `app.js`: 저장 결과를 목록·상세·단계 건수에 연결한다.
- `data.js`: 시연용 상태·기간·기준을 명시한다.
- `project-list.js`, `project-detail.js`: 합의 여부를 범위 내용과 함께 보여준다.
- `scope.test.cjs`: 잘못된 전환과 실패 상황에서 기존 상태가 보존되는지 확인한다.

면접 설명 예: ‘평가 범위가 입력됐다는 사실과 고객과 합의됐다는 사실을 나눴습니다. 합의 완료를 저장해도 바로 단계를 바꾸지 않고, 필수 정보가 갖춰진 상태에서 별도 수집 시작 버튼으로 이동합니다. 브라우저 저장에 성공한 뒤 화면에 반영해서 저장 실패 시 단계만 먼저 넘어가지 않도록 했습니다.’
