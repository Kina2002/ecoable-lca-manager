# WEB-013 담당자 기록과 범위 정의 시작

## 1. 목적과 합의

새 프로젝트는 계약·착수에서 시작했지만 범위 정의로 넘길 수 없었다. 고객 쪽 협의 대상과 우리 쪽 업무 담당자를 기록하고 다음 단계로 넘기는 흐름을 연결한다. 사용자에게 제안한 담당자 두 명과 별도 ‘범위 정의 시작’ 버튼 구현을 승인받았다.

F-01 프로젝트 관리의 담당자·1→2 단계 이동 일부다. F-02 전체 확인 필요 정보, 고객 연락처 데이터베이스, 직원 관리나 실제 연락 기능을 완성한 것이 아니다.

## 2. 사용자에게 설명할 뜻

| 입력 | 의미 | 예시 |
|---|---|---|
| 고객 담당자 | 고객 회사에서 자료 요청·범위 협의를 할 사람 | 김고객 |
| 담당 연구원 | 우리 쪽에서 프로젝트를 맡을 사람 | 박연구 |

현재는 가상 이름을 프로젝트에 직접 기록하는 간단한 버전이다. 실제 사람 선택·로그인·권한·담당자 ID 참조나 이메일·전화번호 입력은 구현하지 않는다. 이름이 적혔다고 고객의 동의나 연락이 실제로 이루어진 것을 의미하지 않는다.

## 3. 화면과 동작

- 계약·착수 단계 프로젝트의 상세 → 개요·범위 위쪽에 **담당자와 착수 준비**를 보여준다. 범위 입력까지 긴 스크롤을 내릴 필요 없이 착수 정보를 기록한다.
- 두 이름은 각각 앞뒤 공백을 정리하고 최대 100자까지 저장한다. 한 사람만 또는 빈 값으로 초안 저장할 수 있다.
- **담당자 저장**은 이름만 기록하고 계약 단계·범위 합의 상태·범위 내용은 유지한다.
- 두 이름을 모두 저장하면 별도 **범위 정의 시작**을 사용할 수 있다. 누르면 **1→2**로 이동한다.
- 입력 중인 담당자나 범위 변경이 있으면 시작을 비활성화하고 먼저 저장하도록 안내한다. 다른 폼을 저장해도 아직 저장하지 않은 입력칸은 다시 만들거나 지우지 않는다.
- 범위 정의로 넘기면서 합의 상태를 강제로 협의 중·확정으로 바꾸지 않는다. 기존 미정·고객 요청안 등의 상태를 유지한다.
- 단계별 건수·프로젝트 목록 소속을 갱신한다. 현재 계약 필터를 보고 있었다면 돌아온 목록에서 프로젝트가 사라지는 것은 정상이다. 범위 정의 필터에서 찾을 수 있다.
- 이동 후에는 범위 기록 쪽 안내에 초점을 옮긴다. 범위 정의 이후에는 두 이름을 요약에서 읽기만 한다.
- 범위 상태에서 수정 칸으로 바로 가기는 기존 사용자 지시대로 **프로젝트 상세 안에서만** 유지한다.

## 4. 단계 조건

1. 현재 계약·착수 단계여야 한다.
2. 저장된 고객 담당자와 담당 연구원이 모두 비어 있지 않아야 한다.
3. 저장 직전 최신 프로젝트 기록과 화면을 열 때/마지막 저장 때의 기록이 같아야 한다.
4. 저장 성공 후에만 2단계로 반영한다.

계약→수집으로 건너뛰기, 2단계 이후 재시작·담당자 수정, 단계 되돌리기는 이번에 허용하지 않는다. 2→3은 기존 범위 확정·필수 정보 검사·별도 수집 시작 버튼을 사용한다. 기획의 킥오프 일정·실제 계약 증빙·인원 마스터 등 전체 착수 관리가 아니다.

기존 `rules.js`의 `gateCheck('assigned')`는 담당자 ID를 가정하는 미연결 규칙이다. 이번 이름 입력을 그 규칙 전체 구현으로 설명하지 않는다. 화면에서 사용하는 이름·단계 검사는 `scope.js`에서 처리한다.

## 5. 보관과 기존 기록 호환

- 기존 `ecoable-lca-manager.scope.v1`에 선택 필드 `customerContactName`, `researcherName`을 추가한다. 범위·단계·담당자를 같은 저장 작업으로 반영하기 위해 이 저장소를 확장한다.
- 기존 필드가 없는 v1은 읽을 때 빈 이름으로 보완하며 읽기만으로 저장하지 않는다. 기존 미정·협의 내용·확정·수집 이동·자료 요청 기록을 유지한다.
- 원래 1단계 프로젝트는 저장된 두 이름이 있어야 2·3단계 기록을 인정한다. 3단계는 기존 범위 확정 조건도 필요하다.
- 원래부터 2단계 이상이던 가상 샘플은 담당자 기록이 없더라도 기존 단계를 유지한다. 가상 인물을 임의로 채우거나 과거 프로젝트를 계약 단계로 되돌리지 않는다.
- 범위 저장으로 담당자나 단계를 우회 변경할 수 없다. 담당자 저장·범위 정의 시작·수집 시작을 각각 별도 메서드로 처리한다.
- 저장 실패·손상·잘못된 이름 형식·알 수 없는 ID·다른 화면에서의 변경은 오류로 알리고 기존 저장본과 단계를 보존한다.
- 현재 기록 한 건이며 담당자 변경 이력·다중 사용자 잠금·서버 동기화를 제공하지 않는다.

## 6. 확인 방법

1. 새로 등록한 프로젝트 또는 이음모빌리티의 계약 단계 상세를 연다.
2. 고객 담당자만 저장한다. 단계는 계약이며 시작은 불가능한지 확인한다.
3. 담당 연구원도 입력해 저장한다. 단계가 여전히 계약인지 확인한다.
4. 범위 정의 시작을 누르고 현재 단계와 위쪽 건수 변경을 확인한다.
5. 새로고침하고 범위 정의 필터로 찾아 두 이름과 단계가 남는지 확인한다.
6. 범위 정보와 합의 상태를 확정 저장한 뒤 기존 수집 시작 버튼으로 3단계까지 이동한다.

## 7. 검증과 한계

- `node --test web/tests/*.test.cjs`: **96개 통과**, 기존 86개와 착수 관련 10개다.
- 이름 정리·빈/한 명 저장·형식과 100자·별도 이동·범위 내용 유지·재로딩·중복 이동과 되돌리기 방지·저장 실패·다른 화면 충돌·구형 v1 무쓰기·손상 보호를 확인했다.
- 새 등록 프로젝트에서 **등록→담당자→범위 정의→확정→수집**을 연결하고 이름·메모·3단계·건수를 복원하는 통합 검사에 통과했다.
- 변경 JavaScript 구문·HTML 정적 연결·HTTP 200·공백 오류를 확인했다.
- 브라우저 접근은 이전 보안 정책 차단을 우회하지 않았다. **실제 입력·버튼 비활성화·클릭·초점·스크롤·작은 화면은 미확인**이며 사용자 화면 확인이 필요하다.

## 8. 파일과 면접 설명

- `scope.js`: 이름 저장과 1→2·2→3 조건, 기존 기록 호환.
- `views/scope.js`: 착수 폼과 공유 저장 상태, 두 폼의 미저장 변경 안내.
- `project-detail.js`: 착수 폼 위치와 이름 요약.
- `app.js`: 이동 결과·목록·단계 건수 갱신.
- `kickoff.test.cjs`: 보호 조건과 전체 시작 흐름 검사.

면접 설명 예: ‘새 업무를 등록한 다음 고객 쪽 협의 대상과 내부 담당자를 기록하도록 했습니다. 담당자를 저장하는 것과 업무 단계를 넘기는 것을 분리해, 두 사람이 저장된 뒤 별도 시작 버튼으로 범위 정의에 들어갑니다. 단계는 저장 성공 후에 바뀌고 기존 범위·자료 기록은 유지됩니다.’
