# 업무 이해와 후속 기능 논의 기록

## 2026-10-18 프로젝트 완료와 삭제 재확인 (WEB-038)

사용자는 다음 기능으로 제안한 프로젝트 완료 처리에 동의하며 생성 프로젝트 삭제 버튼도 요청했다. 이어 삭제는 한 번 더 확인하는 문구창을 명시적으로 요청했다. 인증·등록/고객 최종 확인 뒤 완료일과 기존 보고서·번호를 연결해 10단계로 옮기며, 사용자 생성 프로젝트만 회사명·번호·함께 삭제할 기록을 확인창에서 보여주고 삭제를 다시 눌러 제거한다. 기본 취소 초점과 백업 안내, 관련 기록 삭제·다른 프로젝트 보존·저널 보호를 연결했다. 실제 완료·삭제 실행 시험은 하지 않았다.

## 2026-10-18 백업 파일과 저장 위치 선택 (WEB-037)

사용자는 백업 대상이 앱에 입력해 저장한 기록이고 첨부파일 원본은 아니라는 설명을 들었다. 로컬 백업 파일을 내려받아 OneDrive·USB 등에 보관하고 다른 컴퓨터에서 읽어 복원하는 방식에 동의하며 저장할 폴더 선택도 요청했다. 설정에 위치 선택/기본 다운로드, 파일 미리보기와 현재 기록 선백업·교체 확인을 추가했다. 브라우저의 파일 선택 지원 한계를 안내하고 파일 선택만으로 복원하지 않는다. 실제 파일/복원 실행 시험은 하지 않았다.

## 2026-10-18 앱 이름과 홈 바로가기 요청 (WEB-036)

사용자는 에코에이블 브랜드를 LCA 프로젝트 관리로 바꾸고 해당 영역을 누르면 홈으로 이동하길 요청했다. 용어사전을 메뉴 맨 아래로 옮기고 홈 우선 할 일도 주의 프로젝트처럼 클릭해 바로 관련 기록으로 이동하게 요청했다. 브랜드 홈 링크와 메뉴 순서를 바꾸고 할 일 탭/홈의 공통 이동 함수에 출발 화면별 복귀를 연결했다. 초기 표시만 확인했고 클릭·상세 이동·복귀 시험은 하지 않았다.

## 2026-10-18 별도 홈 탭 구현과 배치 정정 (WEB-035)

사용자가 자료 수집·승인 현황과 주의 프로젝트·할 일 요약의 홈 대시보드 구현을 승인했다. 구현 중 프로젝트 탭 안에 넣지 말고 홈 탭을 따로 만들라고 정정했다. 이에 홈을 독립 주 메뉴·초기 화면으로 만들고 프로젝트 목록·단계·필터는 프로젝트 탭에 유지했다. 수집률은 등록 요청 중 받은 자료, 승인률은 받은 자료 중 승인 자료다. 보완 자료는 받은 기록에 포함하며 요청 0건을 100%로 표시하지 않는다. 각 요약은 3건만 보여주고 상세·할 일로 연결한다. 초기 화면만 확인했으며 전체 계산·메뉴 왕복 시험은 하지 않았다.

## 2026-10-18 할 일 분류 설명 요청 (WEB-034)

사용자는 각 분류의 뜻을 질문한 뒤 분류 버튼 아래·검색 위에 한 줄 설명을 요청했다. 선택한 분류마다 짧은 설명을 표시한다. 최신 기록 확인은 앱에 저장된 기록을 다시 읽어 목록을 계산하는 버튼이며 저장·전체 페이지 새로고침은 아니라고 설명했다. 분류 규칙과 버튼 동작은 그대로 유지한다.

## 2026-10-18 할 일 탭 승인 (WEB-033)

사용자가 다음 기능을 물었고, 별도 수동 입력 없이 기록에서 급한 자료·보완·의견·정보 누락을 모으는 오늘 할 일을 제안했다. 사용자가 할 일 탭 구현을 승인해 주 메뉴에 추가했다. 받은 자료의 검토 지연과 미제출을 구분하고 원래 기록의 승인/종결로 목록을 갱신한다. 일곱 유형·담당 연구원·검색과 해당 기록 이동·복귀를 제공한다. 만료/갱신·수동 할 일·홈 대시보드 보강·백업은 별도 후속이다. 초기 표시만 확인했으며 전체 분류·이동 흐름 실행 시험은 하지 않았다.

## 2026-10-18 두 자료 등록 영역 접기·펼치기 요청 (WEB-032)

사용자는 일괄 등록과 개별 등록 모두 접고 펼칠 수 있기를 요청했다. 두 폼을 독립적으로 접고 펼치며 처음에는 둘 다 접는다. 작성 중 내용을 초기화하지 않고 요청 목록은 아래에 유지한다. 저장·업무 단계·기존 자료 필터는 바꾸지 않는다. 구문·초기 배치 확인만 하고 입력 유지·저장 시험은 하지 않았다.

## 2026-10-18 자료 요청 일괄 생성 승인 (WEB-031)

반복 입력 개선을 마친 뒤 사용자가 다음 추천 기능 구현을 승인했다. 앞서 제안한 순서에 따라 자료 요청 일괄 생성을 진행한다. 필요한 구분을 여러 개 골라 공통 기한과 기본 문장으로 등록하고 필요한 문장만 수정한다. 이미 등록한 구분은 그대로 둔다. 프로젝트별 자료 수집 마감일은 선택적으로 가져오며 기존 개별 등록과 두 자료 필터를 보존한다. 저장은 요청 기록 생성이고 메일 발송·자동 단계 이동은 하지 않는다. 구문·공백·초기 화면 배치만 확인했고 실제 등록 시험은 하지 않았다. 오늘 할 일·대시보드·백업은 다음 별도 합의다.

## 2026-10-18 반복 입력 줄이기 승인 (WEB-030)

사용자가 수동 입력이 많아 불편하다고 지적했다. 남은 기획을 정리한 뒤 반복 입력 개선을 먼저 하기로 했다. 프로젝트 담당자를 기록자 기본값으로 접어서 표시하고 수정·연구원 선택을 제공한다. 실제 내부 검토자는 별도로 지정한다. 실제 업무 날짜는 오늘·달력으로 선택하고 저장 시각과 구분한다. 다음 외부 검증 차수에는 이전 기관·담당자를 불러오고 출처를 표시하며 입력 중에는 덮어쓰지 않는다. 보고서 다음 버전도 표시한다. 의견·답변·변경 사유·확인 체크는 사람이 작성한다. 파일 첨부·로그인·자동 추출·내부 계산·임시 저장은 이번 범위에 넣지 않았다. 구문·공백·초기 화면 배치만 확인했고 실제 저장·차수 시작 흐름은 확인하지 않았다.

## 2026-10-18 내부/외부 검토 분기와 미정 승인 (WEB-029)

사용자는 검증기관·담당자·차수와 지적의 의미를 질문한 뒤 모든 LCA가 제3자 검증이 필요한지 확인했다. 외부 검증 필요 여부를 설명하는 과정에서 내부/외부 두 방식으로 정리하기를 원했고, “그럼 그렇게 해보자” 승인 뒤 미정도 포함해 달라고 했다. WEB-029에서 미정/내부 검토/외부 검토를 선택하고 근거와 내부 확인 기록을 보관하도록 구현했다. 외부 경로도 우리 팀 내부 확인을 거친다. 제도·고객 요구에 맞는 방식은 사람이 결정하며 앱이 의무 여부를 판정하지 않는다.

기존 외부 전용 8단계와 탭은 검토·검증으로 바꾸고 내부는 외부 차수 없이 보고서 확정 및 후속 제출을 연결한다. 미정이면 관련 완료·시작을 보류한다. 실제 외부 차수를 이미 시작했다면 내부/미정으로 바꿔 지적 처리를 건너뛰지 못한다. 기존 외부 기록과 인증 완료 사본은 보존하고 내부 기록을 임의 생성하지 않는다. 구문·공백·미정 초기 화면만 확인했으며 테스트 추가·실행과 실제 저장/전환/호환 실행 확인은 남아 있다. 내부 지적별 관리·외부 철회/재개·제도별 자동 판단·9→10은 별도 합의한다.

## 2026-10-18 검증 완료와 인증·등록 (WEB-028)

사용자는 다음 기능인 검증 완료 기록·별도 8→9·제출 상태와 최종 번호·날짜 구현을 하위 에이전트에게 맡겼다. 인증이 모든 LCA의 의무는 아니므로 인증/등록/고객 제출로 구분한다. 검증 완료는 최종 보고서와 검증 기록 사본을 보관하며 단계는 8에 남는다. 보완으로 근거가 바뀌면 완료 기록을 다시 남겨야 한다. 별도 확인으로 9단계에 들어간 뒤에는 이미 제출할 근거를 묵시적으로 바꾸지 않도록 이전 평가 자료·계산·해석·보고서·검증을 읽기 전용으로 보관한다. 제출 후 보완 요구는 메모와 재제출 상태를 기록하며, 보고서 재작성용 9→8 재개·새 제출 차수는 후속이다. 만료·갱신·정기 점검·9→10은 이번에 추가하지 않는다. 구문·공백과 초기 탭 표시만 확인했고 실제 저장·이동·상태 전환 및 테스트는 실행하지 않았다.

## 2026-10-18 제3자 검증 관리 승인 (WEB-027)

고객 검토 기능 뒤 사용자는 다음 기능을 물었고, 최신 보고서·고객 의견 처리 상태를 확인한 7→8 시작, 검증기관·담당자, 지적/보완 기한/답변/상태, 1차·2차 구분과 수정 보고서 연결 제안에 “구현해보자”로 승인했다. WEB-027로 구현했다. 지적 종결은 검증자의 확인 내용과 근거를 사람이 기록하는 동작이며 공식 검증 통과나 인증 판정은 아니다.

차수 시작 당시 보고서를 고정하고, 지적은 그 보고서를 대상으로 보관한다. 수정 보고서는 더 나중 버전으로 연결한다. 보고서를 보완할 수 있게 8단계의 해석·새 보고서 저장을 허용한다. 현재 지적을 모두 종결하고 담당자가 이전 검토 완료를 확인한 뒤 다음 차수를 시작하며 과거 차수는 그대로 읽는다. 고객 검토는 기존대로 7단계만 쓰고 8단계에서는 조회한다. 첫 차수와 8단계 진입을 새 검증 키에 함께 보관해 일부 저장 실패로 분리되지 않게 했다. 8→9·자료 질의·메일·내부 계산·AI는 추가하지 않았다. 구문·공백·초기 화면만 확인했고 테스트 추가·실행 및 실제 저장·종결·후속 차수 실행 확인은 남아 있다.

## 2026-10-18 고객 검토 의견 구현 승인 (WEB-026)

사용자는 전체 구현 현황을 확인한 뒤 다음 기능을 물었다. 보고서 버전별 고객 의견·답변·열림/답변됨/종결·수정 반영 버전과 보고서 변경 기록 연결을 제안했고 “응 만들어보자”로 승인했다. WEB-026으로 고객 검토 탭과 기록·연결을 구현했다. 처음 받은 의견과 답변 이력은 보존하고, 종결 후 추가 처리가 필요하면 사유를 적고 다시 연다. 설명으로 해결한 의견은 수정 보고서 없이 종결할 수 있다. 답변 기록은 고객에게 보내거나 고객 동의를 확인하는 기능은 아니다.

의견을 받은 보고서와 그 의견을 반영한 나중 보고서를 구분한다. 보고서 새 버전은 관련 의견 원문을 사본으로 보관하고 이후 상태 변경으로 본문을 덮어쓰지 않는다. 실제 적용과 종결은 고객 검토 탭에서 담당자가 판단해 저장한다. 기존 자유 메모를 실제 의견으로 임의 변환하지 않는다. 7→8·제3자 검증 지적·검토 라운드·메일·AI·내부 계산은 이번에 추가하지 않았다. 구문·공백과 초기 화면 표시만 확인했으며 테스트 추가·실행은 없고 저장·답변·종결·재개의 실제 실행 확인은 남아 있다.

## 2026-10-18 완료 확인 배치 교정 (WEB-025)

사용자는 자료 수집 완료 확인이 왜 자료 요청 탭 밖에 있는지 질문했다. 프로젝트 전체 단계 이동을 공통 상단에 두었던 의도와 실제 자료 확인 흐름의 차이를 설명했고, 사용자가 자료 요청 안으로 이동하도록 요청했다. 수집·검토 완료 확인을 해당 탭 상단에 배치하고 불필요한 탭 이동 버튼을 제거했다. 단계 조건과 기존 입력 자료는 유지한다.

## 2026-10-17 자료 검토 완료와 계산 단계 이동 승인

사용자는 검토 단계에 승인 건수와 미승인 자료 안내를 표시하고 모두 승인되면 별도 버튼으로 계산(모델링) 단계로 이동하는 기능을 승인했다. WEB-019는 요청 0건을 완료로 보지 않고, 받은 자료·검토·승인 기록을 확인한 뒤 4→5만 저장한다. 실제 환경영향 계산이나 5→6은 후속 범위다. 기존 자료·승인 기록과 필터·초안은 유지한다.

## 2026-10-17 자료 수집 완료와 검토 시작 승인

사용자는 모든 요청 자료가 제출됐는지 확인한 뒤 별도 버튼으로 데이터 수집에서 데이터 검토로 이동하는 기능을 승인했다. 요청이 0건이거나 요청·보완 요청이 남으면 이동을 막고 해당 항목을 안내한다. 제출됨·검토 중·승인 자료는 제출 확인에 포함한다. 버튼을 누르면 프로젝트는 3→4단계로 이동하고 수집 D-day를 자료 수집 완료로 표시하지만 자료별 검토·승인 기록은 바꾸지 않는다. WEB-018에 구현·호환·확인 결과를 기록했다.

## 2026-10-17 자료 현황 D-day의 기준 교정

사용자는 자료 수집이 끝나지 않았는데 요청 기록이 없다는 이유로 D-day가 나오지 않는 점을 지적했다. 자료 현황 D-day는 별도로 정한 자료 수집 마감일을 기준으로 하며, 아직 자료 수집 일정을 이야기하지 않았을 수 있는 계약·범위 단계에는 미정을 허용하기로 했다. WEB-017에 날짜 저장·비우기와 목록 표시를 구현했다. 요청 0건과 수집 완료는 별개이며, 자료 검토 이후 단계에서는 자료 수집 완료를 표시한다. 아래 WEB-016 논의는 변경 전 기록이다.

기록일: 2026-10-16. 사용자가 프로그램의 업무 의미를 이해하고 면접에서 설명할 수 있도록 나눈 대화를 정리한다.
확정한 설명, 구현한 기능, 후속 제안을 구분한다. 이 문서 작성이 새 기능 구현 승인을 뜻하지 않는다.

## 1. 받은 자료와 최종 결과의 차이

- 회사가 보내준 고지서·엑셀·검침 기록 등을 보고 앱에 받은 자료를 기록한다. 대화에서 ‘원자료’라고 부른 것은 이 회사 제공 자료를 뜻하며 별도의 다른 자료가 아니다.
- 12,000 kWh는 전력 사용량을 나타내는 활동량이다. 최종 탄소배출량이나 환경영향 결과가 아니다.
- 실제 자료는 월별·공정별·사업장별로 여러 행과 파일을 포함할 수 있고, 회사가 합계를 정리해서 제공할 수도 있다.
- 현재 WEB-007은 요청당 받은 자료의 현재 기록 한 건을 보관하는 단순한 첫 버전이다.
- 상세 기록과 증빙 연결은 사용자가 나중에 구현하기로 했다. 지금 구조를 여러 행·실제 파일 저장으로 바꾸지 않는다.

자세한 결정: [WEB-007 10절](WEB-007-received-data.md#10-후속-논의-기록-상세-자료와-증빙).

## 2. 검토는 무엇을 확인하는가

처음 제안한 ‘값과 단위가 원자료와 일치하는가’는 회사 자료를 앱에 옮겨 적을 때의 입력 실수를 재확인한다는 뜻이었다.
사용자와 대화한 결과, 이번 검토 기능의 중심은 **회사에서 받은 자료 자체가 요청에 맞는지 확인하는 것**으로 정했다.
따라서 입력값 대조는 이번 체크 목록에서 제외했다.

합의하고 WEB-008에 구현한 세 가지 항목:

1. 요청한 기간의 자료인가?
2. 요청한 제품·사업장에 해당하는 자료인가?
3. 요청한 항목과 증빙이 빠짐없이 있는가?

예: 1~12월 자료를 요청했는데 12월분이 빠졌다면 사유를 적어 보완 요청한다.
검토는 사람이 원본을 보고 판단하며 앱은 체크·메모·결과를 저장한다. AI나 앱이 파일 내용을 자동 판정한 것이 아니다.
승인은 담당자의 자료 검토 승인이지 제품 인증 완료가 아니다. 이 세 항목은 시연 앱의 기본 확인 목록이며 회사의 공식 심사 기준으로 설명하지 않는다.

구현·검증 범위: [WEB-008](WEB-008-data-review.md). 브라우저 접근 제한으로 실제 UI 확인이 추가로 필요한 상태도 해당 SPEC에 기록했다.

## 3. 검토 버튼과 자료 상태

| 버튼 또는 행동 | 자료 상태·의미 |
|---|---|
| 받은 자료 저장 | 제출됨: 자료를 받았다는 기록 |
| 검토 시작 | 검토 중: 담당자가 확인하기 시작함 |
| 검토 내용 저장 | 검토 중 유지: 일부 체크·메모를 중간 저장함 |
| 보완 요청 | 보완 요청: 필수 사유를 적고 부족한 자료를 다시 받음 |
| 승인 | 승인: 세 항목을 모두 확인하고 결과를 저장함 |
| 받은 자료를 다시 저장 | 제출됨 복귀: 이전 체크·메모·결과를 초기화하고 새 자료를 검토함 |

‘검토 내용 저장’은 상태 이름이 아닌 버튼 이름이다. 목록에서 구분할 상태는 ‘검토 중’이다.
현재 카드에 상태와 검토 요약을 표시한다. 상태별 건수·필터는 아직 구현하지 않았다.

## 4. 자료 상태와 프로젝트 단계는 별개

| 구분 | 대상 | 예시 |
|---|---|---|
| 프로젝트 단계 | 프로젝트 전체의 업무 진행 | 범위 정의, 데이터 수집, 데이터 검토, 계산 |
| 자료 상태 | 요청한 자료 각각의 진행 | 요청, 제출됨, 검토 중, 보완 요청, 승인 |

프로젝트가 ‘데이터 수집’ 단계여도 먼저 도착한 전력 자료를 검토할 수 있다.
다른 자료가 아직 도착하지 않았다면 프로젝트 전체를 같은 속도로 옮기는 것은 아니다.

상태 필터의 ‘검토 중’이나 ‘보완 요청’을 누르는 것은 그 자료만 골라 보는 동작이다. 프로젝트를 다른 단계로 옮기지 않는다.
현재 앱은 자료 상태를 바꿔도 프로젝트 단계가 그대로다.
프로젝트 단계 전환은 별도 미구현 기능이다. 설계서의 수집 완료·승인 완료 조건 등을 확인해 해당 기능에서 함께 구현한다.
대화에서 필요한 자료가 모두 제출되면 데이터 검토로, 모두 승인되면 계산으로 이동하는 흐름을 설명했으나, 세부 예외와 전환 버튼·제안 방식은 구현 시 정한다.

## 5. 범위 정의의 의미

범위 정의는 ‘이번 프로젝트에서 어떤 제품을 어떤 기준량·기간으로 어디까지 평가할지’ 정리하는 단계다.
예를 들어 제품 모델, 대상 공장, 패널 1장 같은 기준량, 원료~생산 또는 사용·폐기 포함 여부, 자료 기준기간을 확인한다.
평가 범위에 따라 받아야 할 자료가 달라지므로 자료 요청·수집보다 먼저 정리한다.

고객사와 컨설팅 회사의 역할은 의뢰 내용·고객 준비 정도·계약에 따라 달라질 수 있다.
설명을 위한 일반적인 흐름은 다음과 같다. 특정 회사의 실제 내부 절차를 확인한 것은 아니다.

1. 고객사가 목적과 요구사항을 제시한다. 예: 거래처 탄소정보 제출, EPD 등록, 내부 개선 검토.
2. 고객사가 구체적인 거래처 요구서·양식을 가진 경우 컨설팅 회사가 그 요구와 적용 기준을 확인하고 실행 범위를 구체화한다.
3. 목적만 정해 의뢰한 경우 컨설팅 회사가 목적에 맞는 대상과 범위를 제안할 수 있다.
4. 적용 기준을 지키는 범위에서 고객사와 평가 범위를 확인·합의한다.

인증·EPD처럼 적용 규칙이 있는 경우 양쪽이 임의로 필수 평가 범위를 줄이는 것으로 설명하지 않는다.
우리 앱의 범위 정의는 **고객 요구와 적용 기준을 확인해 합의한 평가 범위를 기록하는 단계**다.
컨설팅 회사가 혼자 자유롭게 정하는 단계라는 의미가 아니다.

설명에 참고한 공식 출처:

- [GHG Protocol 제품 표준](https://ghgprotocol.org/sites/default/files/standards/Product-Life-Cycle-Accounting-Reporting-Standard-EReader_041613_0.pdf): 업무 목적, 평가 범위, 자료 수집·계산의 관계.
- [EPD International 개발 절차](https://www.environdec.com/getting-started/epd-development): 적합한 PCR 선택과 해당 규칙에 따른 LCA 수행.

## 6. 후속 기능과 현재 추천

**프로젝트 안의 자료 상태별 건수·목록 필터:** 추천 후 사용자가 먼저 구현하자고 승인해 [WEB-009](WEB-009-request-status-filter.md)로 구현했다. 실제 화면 확인 제한은 해당 SPEC에 기록한다.

- 전체·요청·제출됨·검토 중·보완 요청·승인의 건수를 표시한다.
- 상태 버튼을 누르면 현재 프로젝트에서 그 상태인 요청만 보여준다.
- 삭제한 요청은 현재 건수에서 제외하고, 기존 삭제 목록에서 별도로 다룬다.
- 프로젝트 단계와 실제 자료 상태는 필터 동작으로 변경하지 않는다.
- 예: ‘보완 요청 2’를 누르면 보완해야 할 자료 두 건만 확인한다.

사용자가 검토 결과를 나눠 보고 싶다고 질문한 내용과 직접 연결되는 작은 후속 기능으로 추천한다.
필터는 현재 프로젝트의 자료 조회이며 프로젝트 단계 전환과 구분한다.

이전에 기록한 상세 자료·증빙 연결, 실제 공개 데이터 표본, AI 요청문/메일 작성과 메일·파일에서 자료 추출은 기존 대기 목록을 유지한다.
상세 범위와 구현 순서는 사용자와 다시 정한다.

## 7. 초기 단계의 범위 값과 다음 작업 순서

사용자는 계약·범위 정의 단계인 가상 프로젝트에도 ‘요람~문’ 같은 경계 값이 보여 이미 범위가 확정된 것 같다고 지적했다.
현재 샘플이 값을 미리 채우고 요청안·협의 중·확정 여부를 표시하지 않아 혼동될 수 있다는 점을 설명했다.
범위 값이 있다는 것과 합의·확정됐다는 것은 구분한다. 계약 단계라도 고객 요구안이 있을 수 있으므로 단계 번호만으로 범위 확정을 판단하지 않는다.

사용자가 지정한 순서:

1. WEB-009 자료 상태별 건수와 필터를 먼저 구현한다.
2. 그다음 범위의 미정·고객 요청안·협의 중·확정 표시를 추가한다. **바로 다음 작업이다.**

사용자는 협의가 확정되면 수집 단계로 넘어가는지 질문했다.
범위 합의와 필수 정보가 갖춰지면 데이터 수집으로 진행하는 업무 흐름은 맞지만, 시스템 경계의 확정 하나만으로 자동 이동하는 것으로 설명하지 않는다.
기준량·시스템 경계·기준기간·적용 기준 등 조건과 단계 이동 방식은 범위 상태 작업에서 함께 정한다.
WEB-009는 범위 상태와 프로젝트 단계 이동을 구현하지 않는다.

## 8. 필터 배치에 대한 사용자 교정

사용자가 원한 것은 상단 ‘데이터 수집’ 단계 필터 안에서 다시 자료 상태를 고르는 하위 필터였다.
프로젝트 상세 안에만 필터가 있으면 여러 번 들어가야 하고 한눈에 보이지 않는다는 문제를 지적했다.
따라서 수집 단계 선택 직후 그 단계 프로젝트들의 자료 건수와 상태별 목록을 표시하도록 WEB-009를 보완했다.

사용자는 별도로 **기존 프로젝트 상세의 필터도 없애지 말라**고 요청했다. 한 회사가 많은 자료를 제출할 때 사용할 수 있기 때문이다.
수집 단계 하위 필터는 단계 안의 여러 프로젝트를, 상세 필터는 회사별 자료를 조회하는 역할로 둘 다 유지한다.
원래 지정한 다음 작업인 범위 상태 구분은 이 배치 교정을 완료한 뒤 진행한다.

## 9. 범위 상태와 수집 시작 방식 확정 (2026-10-16)

사용자는 ‘확정 저장 시 자동 이동’ 대신 **‘데이터 수집 시작’ 버튼으로 이동**하는 추천안을 선택했다.
네 상태는 합의 여부, 프로젝트 단계는 업무 전체의 진행 위치다. 확정 저장은 단계를 유지하고, 범위 정의 단계에서 필수 정보와 확정 여부를 확인한 뒤 버튼으로 수집 단계에 넘긴다.

[WEB-010](WEB-010-scope-status.md)에 구현·검증·한계를 기록했다. 기준량·경계 외에 없던 기준기간·적용 기준 입력을 연결했다. 12개월 이외의 기간은 사유를 남긴다. 이는 시연용 최소 조건으로, 전체 범위 조건이나 적용 기준별 적합성 심사는 아니다.

네 상태를 반드시 순서대로 거치도록 강제하지 않는다. 계약 단계에 고객 요청안이 있을 수 있고 합의됐다는 기록도 가능하나, 계약에서 수집으로 바로 건너뛰지는 않는다. 수집 이후 재협의·되돌리기는 별도 후속 논의다.
기존 회사별 자료 필터와 수집 단계 안의 하위 필터는 유지한다. 사용자 브라우저 기록을 초기화하지 않는다.

## 10. 협의 메모와 범위 상태 바로 가기

사용자는 협의 내용을 직접 적을 수 있기를 요청했고 범위 입력칸까지 스크롤이 길다고 지적했다. [WEB-011](WEB-011-scope-memo-shortcut.md)에 선택 메모와 상세 상태 버튼의 바로 가기를 구현했다. 수집 이후 읽기 전용 정책은 유지한다.

12개월이 아닌 기간의 사유는 신규 가동 등으로 자료 기간이 짧거나 길어진 이유를 설명하는 칸이라고 안내했다. ‘공장이 7월에 시작돼 6개월 자료만 있음’ 같은 예시다. 이는 앱의 기본 기간과 다른 이유를 남기는 것으로, 실제 적용 기준별 기간·대표성 적합성을 자동 판단하는 기능은 아니다.

사용자가 바로 가기의 위치를 **프로젝트 상세 창에서만**으로 정정했다. 목록 상태는 글자로 되돌렸고 상세 바로 가기와 메모는 유지한다.

## 11. 새 프로젝트 등록 승인

사용자는 WEB-011 상세 전용 바로 가기를 확인했고, 다음 기능으로 새 프로젝트 등록을 승인했다. 샘플 7개 조회에서 직접 새 업무를 시작할 수 있게 한다. [WEB-012](WEB-012-project-create.md)로 회사명·제품명·업무 목적·목표일을 입력받고 계약·착수 단계 및 범위 미정으로 시작한다. 등록 성공 후 계약 단계 필터로 전환해 새 프로젝트를 찾기 쉽게 한다.

지금은 가상 시연이므로 직접 등록한 회사에도 가상을 표시한다. 같은 회사·제품의 반복 의뢰는 별도 번호로 구분한다. 계약→범위 이동이나 기본정보 수정·삭제는 이번 범위에 넣지 않는다.

진행률을 설명할 때 SPEC 작업 수와 큰 기획 기능 수를 구분한다. WEB-012까지 작은 작업 12개이며, 설계서 18개 기능 중 12개 전체 완료라는 뜻은 아니다. 등록도 F-01 중 일부다.

## 12. 담당자와 범위 정의 시작 승인

사용자가 새 프로젝트 등록을 확인했고 다음 제안인 고객 담당자·담당 연구원 기록과 별도 범위 정의 시작을 승인했다. [WEB-013](WEB-013-kickoff-to-scope.md)에 구현했다. 고객 쪽 협의 대상과 내부 업무 담당자의 가상 이름만 기록하며 실제 연락처·직원 마스터·메일을 연결하지 않는다.

담당자 저장은 계약 단계를 유지하고, 두 이름이 저장된 뒤 버튼으로 1→2를 이동한다. 합의 상태는 그대로 유지한다. 등록→착수 담당자→범위 정의→확정→수집의 흐름을 연결했다. 이름 변경 이력·수집 이후 재협의 등은 별도 작업이다.

## 13. 가상 고객 담당자와 우리 측 연구원 메뉴

사용자는 다른 데이터에도 가상 고객 담당자를 넣고 우리 측 연구원 탭을 만들길 요청했다. 연구원별 이름·담당 프로젝트 조회와 등록 후 프로젝트 선택 중 **둘 다**를 선택했다. [WEB-014](WEB-014-researchers.md)로 구현했다.

기본 3명의 가상 연구원과 7개 샘플의 고객 담당자를 지정한다. 직접 저장된 이름·빈 값은 유지하고, 이름만 같다는 이유로 기존 기록을 특정 ID에 자동 연결하지 않는다. 새로 등록한 가상 연구원을 계약 단계 상세에서 선택하고 연구원 메뉴에서 담당 프로젝트를 본다. 이후 단계 재배정·인사·계정·메일은 별도 기능이다.

## 14. 프로젝트 표 검색과 연구원 연결 동선

사용자는 목록에도 담당 연구원을 표시하고, 상세의 담당 연구원을 누르면 그 연구원 탭으로 이동하고, 이미지의 제목 옆 빨간 영역에 검색·필터를 요청했다. [WEB-015](WEB-015-project-search-researcher-link.md)에 검색·담당 연구원·업무 목적을 단계 선택과 AND로 조합해 구현했다. 목록의 범위 상태는 기존 지시대로 일반 글자다.

검색 결과 건수와 상단의 전체 단계 건수를 구분한다. 기존 자료 상태 하위 필터는 유지한다. 상세의 연구원 바로 가기는 ID로 카드에 초점·스크롤·강조를 옮기며 이름만 있는 기록을 특정 사람에게 임의로 연결하지 않는다.

## 15. D-day와 완료 용어의 최종 합의·집 노트북 재개

처음에 기한 경과와 마감 완료의 뜻이 섞여 사용자가 정정했다. 최종 합의는 날짜를 계속 세고 검토·보완 상태를 함께 보여주며 실제 승인은 날짜를 멈추는 방식이다. 날짜는 마감일, 자료 최종 판단은 승인, 프로젝트 최종 상태는 완료로 구분한다. 제출됨은 승인이나 프로젝트 완료가 아니다.

[WEB-016](WEB-016-deadlines.md)에서 프로젝트 목록의 목표일·자료 현황 두 종류와 각 자료의 D-day를 구현했다. 자료 대표값은 삭제되지 않은 미승인 자료 중 가장 이른 기한, 요청 0건은 요청 없음, 전체 승인은 자료 검토 완료다. 검토 중 D+를 고객의 지연으로 단정하지 않는다. 홈 화면에서 급한 자료를 모아보는 것은 후속으로 남긴다.

사용자는 구현 후 지금까지의 코드를 GitHub에 올려 집 노트북에서 이어가길 요청했다. 실행·현재 기능·검사·UI 미확인·다음 작업 전 합의와 브라우저 입력 기록이 자동 이동하지 않는 한계를 루트 CONTINUE-HERE.md에 남겼다. 실제 브라우저 입력 기록은 접근 제한 때문에 추출하지 않았다. 백업/가져오기 기능을 이번 작업에 임의로 추가하지 않는다.

## 16. 계산 단계 자료 인계와 내부 계산 확장 순서 (2026-10-17)

수집 완료는 모든 자료를 받은 시점, 검토 완료는 모두 승인한 시점으로 나누고 WEB-018의 3→4, WEB-019의 4→5를 연결했다. 사용자는 실제 LCA 계산에서 무엇을 구현할지 질문한 뒤, **앱 내부 계산은 AI 연결처럼 모든 기본 기능을 구현한 다음 검토하고 지금 제안한 기능부터 구현**하도록 지시했다.

[WEB-020](WEB-020-approved-export-external-results.md)에서 승인 원자료 CSV와 외부 계산 결과 등록을 구현했다. 원자료의 연간 활동량을 제품당 환경영향 결과로 해석하지 않는다. 외부 도구에서 기준량·범위를 맞춰 계산한 결과와 도구·DB·평가 방법·할당 근거를 사람이 기록하고, 당시 승인 자료를 보관해 근거 변경을 알린다. 앱에서 계산 엔진·계수 DB·AI·파일 내용 분석을 실행하는 기능은 이번 작업에 넣지 않는다. 5→6 이동과 다음 기본 기능도 사용자와 별도로 정한다.

## 17. 결과 해석 확인 후 보고서 초안으로 연결 (2026-10-17)

사용자는 결과 해석 화면을 확인한 뒤 다음 기능 구현을 요청했다. 결과 해석 WEB-021 뒤의 보고서 단계 시작과 초안 정리를 WEB-022로 연결했다. 최신 승인 자료·계산 결과에 맞는 해석을 저장한 뒤 담당자가 버튼으로 6→7을 결정한다. 보고서는 이미 기록한 내용의 사본을 모으며 AI가 원인·개선안을 생성하지 않는다.

보고서 작성 중에도 외부 결과가 바뀔 수 있으므로 7단계의 해석 수정과 해석→초안 순서의 재확인을 허용한다. 초안 본문은 화면 조회·글 파일(.md) 내려받기까지만 구현하며 고객 검토 의견 종결과 제3자 검증 이동은 이번에 넣지 않는다. 이번 테스트 추가·실행은 하지 않았고 화면 표시 외 실행 검증은 남았음을 SPEC에 기록했다.

## 2026-10-17 결과 해석 단계 (WEB-021)

사용자는 5→6 시작과 네 항목의 직접 해석 기록 제안을 하위 에이전트에게 구현하도록 명시했다. 현재 자료가 모두 승인됐고 저장된 외부 결과의 근거가 최신일 때만 별도 버튼으로 이동한다. 해석은 외부 결과 버전·근거에 연결하고 변경 시 다시 확인한다. 앱이 기여도나 개선 효과를 자동 추정하지 않는다. 보고서 단계 이동은 이번 범위에 포함하지 않는다. 내부 LCA 계산과 AI는 기본 기능 완성 후 검토한다. 이번 작업은 자동 테스트 추가·실행 없이 구문·코드 검토와 별도 localhost 실제 UI로 확인했다. 상세는 WEB-021 SPEC을 따른다.

## 18. 보고서 버전 보관과 변경 이력 (2026-10-18)

같은 날 합의한 PDF·Word 내려받기(WEB-023)는 별도 하위 에이전트가 구현했다. 형식별 여러 버튼 대신 접기·펼치기 안의 파일 형식 선택과 공통 내려받기로 만들었다. 외부 변환 서버에 올리지 않고 로컬 라이브러리·글꼴로 실제 문서를 생성한다. 한글·단위·숫자를 보존하며 Word 시각적 렌더는 bundled LibreOffice 부재로 미확인인 한계를 SPEC에 남겼다. 내부 계산·AI 확장은 기본 기능 이후로 유지한다.

사용자는 PDF·Word 내려받기를 하위 에이전트에게 맡긴 뒤 다음 기능을 논의했다. 보고서의 고객 검토 의견 관리 제안을 듣고, 먼저 보고서가 여러 차례 바뀔 수 있으니 각 버전과 무엇을 왜 어떻게 바꿨는지 기록할 공간이 필요한지 물었다. 현재 버전 번호는 저장 횟수이고 최신 한 건만 보관한다는 한계를 설명한 뒤 사용자가 버전별 보관·변경 이력 구현을 승인했다.

WEB-024는 새 버전 저장 때 이전 보고서를 보존하고 변경 내용·사유·전후 내용·작성자·선택 의견 메모를 남긴다. 이전 버전의 당시 자료·계산·해석을 다시 읽고 본문 차이를 비교한다. 과거 보관본은 최신 문서와 구분해 내려받는다. 고객 검토 의견과의 실제 연결은 후속 기능이며 이번 메모를 의견 처리 완료로 보지 않는다. 이력 도입 전 사라진 버전은 복구할 수 없다. 사용자 요청에 따라 부모는 이력 구현을 진행하고 하위 에이전트는 내보내기 작업을 계속 맡았다.
