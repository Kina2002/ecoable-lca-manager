# WEB-045 자료 요청의 ‘해당 없음’과 사유

기준: 설계서 v02 F-04, [기능 체크리스트](../../CHECKLIST.md). 2026-10-19 사용자와 다음 기능을 하나씩 구현하기로 합의한 뒤, ‘자료 해당 없음 처리’를 첫 순서로 선택했다.

## 왜 필요한가

자료가 아직 도착하지 않은 경우와 그 제품·사업장에 아예 발생하지 않는 자료는 다르다. 예를 들어 포장 공정이 없는 제품에 포장재 사용량을 요청했다면, 담당자는 “포장 공정 없음”이라고 근거를 남겨야 한다. 이 항목을 미제출로 계속 세면 허위 지연 알림이 생긴다. ‘해당 없음’은 값 `0`이나 승인과도 다르다. 공정은 있지만 사용량이 0이라면 실제 자료와 근거를 기록해 검토해야 한다.

## 이번 기능의 사용 흐름

1. 프로젝트 상세 → **자료 요청**에서 상태가 **요청**인 항목을 펼친다.
2. **이 자료가 해당하지 않나요?**를 열어 사유를 1~1,000자로 적고 저장한다.
3. 항목에 **해당 없음** 상태와 사유가 표시된다. 상세 상태 필터와 수집 단계의 하위 필터에서도 조회할 수 있다.
4. 잘못 판단했다면 **다시 요청하기**를 누른다. 상태는 요청으로 돌아가고 해당 없음 사유는 제거된다. 이후 받은 자료를 기록할 수 있다.

받은 자료가 이미 있는 제출됨·검토 중·보완 요청·승인 항목은 이번 기능으로 바로 전환하지 않는다. 기존 자료·검토 결과를 몰래 지우지 않기 위해서다. 이 경우에는 기존 기록을 검토하고 필요한 변경을 별도로 결정해야 한다. 삭제·복원은 기존처럼 전체 요청 기록을 보존한다.

## 업무 계산 규칙

- 해당 없음은 미제출/임박 할 일과 D-day 대상에서 빠진다. 요청 카드의 기한 배지는 **해당 없음**으로 고정된다.
- 프로젝트별 수집률·승인률, 수집/검토 완료 조건의 분모에서 제외한다. 완료 확인 화면에는 해당 없음 건수를 따로 표시한다.
- 모든 요청이 해당 없음이면 수집/검토/계산 단계를 완료할 수 없다. 실제로 제출·승인할 자료가 최소 한 건 필요하다.
- 외부 계산 입력 CSV에는 승인 자료만 들어간다. 계산 근거 사본과 보고서에는 해당 없음 항목과 사유를 별도로 남긴다. 사유나 상태가 바뀌면 최신 계산 근거도 달라진 것으로 판단한다.
- 삭제한 요청은 종전처럼 집계에서 제외한다. 프로젝트 단계는 상태 저장만으로 자동 이동하지 않는다.

## 보관과 보호

기존 `ecoable-lca-manager.requests.v1` 저장 키와 `version: 1`을 유지한다. 해당 없음 항목에만 다음 필드를 추가한다.

```json
{
  "status": "해당 없음",
  "notApplicable": {
    "reason": "포장 공정이 없어 포장재 사용량이 발생하지 않음",
    "recordedAt": "2026-10-19T00:00:00.000Z"
  }
}
```

사유는 앞뒤 공백을 제거하고, 빈 문자열·1,000자 초과를 거절한다. 기존 요청은 새 필드 없이 그대로 읽는다. 잘못된 상태/사유/시각을 읽으면 자동 복구로 덮지 않고 변경을 중단한다. 저장 실패 시 기존 원문과 입력을 유지한다. 다른 프로젝트·삭제 요청·이미 상태가 바뀐 요청·9단계 이후 읽기 전용 요청의 쓰기는 거절한다. 브라우저 백업 JSON에 포함되는 기존 요청 저장 키를 사용하며 백업 형식은 늘리지 않는다.

## 구현과 확인

주요 연결: `web/js/requests.js`(상태·저장), `web/js/views/requests.js`(입력·복귀), `web/js/request-filter.js`와 수집 화면(두 필터), `web/js/scope.js`(단계 조건), `web/js/deadlines.js`·`dashboard.js`(현황), `web/js/modelling.js`·`report.js`(계산 근거·보고서), `web/tests/not-applicable.test.cjs`.

- 전체 자동검사 **222개 통과**. 사유 필수·저장 실패·상태 변경 충돌·삭제/복원·두 필터가 공유하는 상태 목록·수집/검토/계산 최소 한 건·계산 결과 재읽기·CSV 제외·보고서 사유 구분을 확인했다.
- 변경 JavaScript 구문 검사와 `git diff --check`를 통과했다.
- 실제 브라우저에서 버튼 클릭과 시각적 배치, 다른 창 동시 사용은 이번 자동검사와 별개로 사용자가 확인할 항목이다. 기존 로컬 미리보기 브라우저 제어는 보안 정책으로 차단되어 자동 조작하지 않았다.

면접에서 이렇게 설명할 수 있다: “고객사가 아직 자료를 보내지 않은 경우와 제품에 애초에 해당하지 않는 경우를 분리했습니다. 담당자가 사유를 남겨야만 해당 없음으로 처리되고, 이 항목은 독촉·기한 경고와 승인 자료 수에서 빠집니다. 잘못 분류했다면 다시 요청 상태로 되돌릴 수 있으며, 계산과 보고서에는 제외한 이유가 남습니다.”
