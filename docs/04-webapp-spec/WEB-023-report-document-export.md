# WEB-023 보고서 PDF와 Word 내려받기

## 1. 합의 범위

2026-10-18 사용자는 보고서를 PDF 또는 Word 양식으로 내려받되, 여러 형식별 버튼 대신 펼쳤다 접는 영역에서 형식을 고르고 공통 내려받기를 누르도록 요청했다. 사용자의 명시적 하위 에이전트 위임으로 구현했다.

저장한 보고서 사본을 실제 PDF와 DOCX 파일로 만든다. HTML에 .doc 확장자를 붙이거나 인쇄 창을 여는 방식이 아니다. Markdown은 기존 호환을 위해 선택지로 유지한다. 내부 LCA 계산·AI 생성·증빙 파일 업로드·고객 검토 의견·7→8 이동은 포함하지 않는다. 후속 보고서 버전 보관과 변경 이력은 WEB-024에서 별도로 구현했다.

## 2. 사용 흐름

1. 보고서 탭의 저장된 보고서 영역에서 **보고서 내려받기**를 펼친다. 기본 상태는 접힘이다.
2. **파일 형식** 선택 상자에서 PDF 문서(.pdf, 기본), Word 문서(.docx), 글 파일(.md) 중 하나를 고른다.
3. 공통 **내려받기**를 누른다. 선택만으로 파일을 생성하지 않는다.
4. 생성 중에는 선택 상자와 내려받기 버튼을 잠그고 ‘파일 만드는 중…’과 상태 안내를 표시한다. 완료나 오류 후 선택한 형식을 유지한다. 접었다 펼쳐도 같은 화면 안의 선택을 유지한다.

기본 내려받기는 최신 승인 자료·계산 결과·해석과 일치하는 저장 보고서가 있어야 한다. 클릭할 때 저장소를 다시 읽는다. 문서 생성이 끝났을 때도 다시 읽어 보고서 버전과 근거를 비교한다. 생성 중 보고서나 자료가 바뀌었다면 파일을 전달하지 않고 다시 확인하도록 안내한다. 저장된 초안과 작성 중인 제목·메모를 변경하지 않는다. WEB-024의 과거 보관본 선택과 구분 안내는 해당 명세를 따른다.

## 3. 문서 내용과 양식

- 제목, 가상 데이터·검토 전 초안 표시, 보고서 버전, 한국 시간 기준 저장 시각
- 프로젝트 번호·회사·제품·담당자, 평가 기준량·범위·기간·적용 기준
- 저장 당시 승인 원자료와 증빙 파일 이름, 검토 메모
- 계산 도구·DB·방법·할당 근거·계산일·결과 파일 이름·계산 메모
- 지표 이름·결과값·단위를 표로 표시
- 담당자 해석 네 항목과 보고서 작성 메모
- 증빙·계산 결과 파일은 이름만 포함되고 실제 파일 내용은 첨부되지 않는다는 설명
- WEB-024에서 전달하는 변경 기록 또는 과거 보관본 안내도 같은 sections(record) 본문을 통해 포함

PDF는 A4, 본문 10pt와 검은 제목·소제목, 여백·페이지 번호·반복 표 머리글로 구성한다. 짧은 첫 문단과 소제목을 함께 배치해 제목만 페이지 아래 남는 것을 줄인다. 첨부 파일 설명은 제목 아래에 표시한다. Word는 실제 OOXML 문서로 Title·Heading 1 스타일, A4 여백, 지표 표와 페이지 번호를 포함해 편집할 수 있다.

한글은 Noto Sans KR, 라틴 문자·아래첨자·주요 수학 기호는 Noto Sans를 사용한다. PDF에는 사용 글리프를, DOCX에는 일반 굵기 한글·라틴 글꼴을 포함한다. 숫자는 재계산하거나 반올림하지 않고 입력 문자열을 유지한다. 1.4300, -1.2e-3, kgCO₂e를 확인했다. 모든 언어·이모지의 글리프를 보장하는 기능은 아니다. 파일명은 가상 표시·프로젝트 번호·보고서 버전과 선택 확장자를 사용한다.

## 4. 로컬 생성과 의존성

`web/js/report-export.js`에서 `LCA.reportExport.create(record, format)`이 Blob과 확장자를 비동기로 반환한다. DOM 본문을 캡처하지 않고 저장된 사본을 `LCA.report.sections(record)`로 읽어 두 문서를 만든다. 사용자 입력은 텍스트로 처리하며 HTML이나 스크립트로 실행하지 않는다.

pdfmake 0.2.20(MIT), docx 9.5.1(MIT), Noto Sans KR 2.004 및 Noto Sans(OFL 1.1)를 `web/vendor/`에 고정 보관한다. 선택 형식에 필요한 라이브러리와 글꼴을 같은 서버에서 필요할 때 읽는다. CDN·외부 변환 API·보고서 업로드는 없다. 인터넷 연결이나 별도 API 키 없이 로컬 미리보기 서버의 파일로 생성한다. 실패한 도구/글꼴 로드는 다음 시도에서 다시 읽을 수 있다.

출처·라이선스·자산 해시는 [vendor 안내](../../web/vendor/README.md)와 [SHA256SUMS](../../web/vendor/SHA256SUMS.txt)에 기록했다. 전체 브라우저 입력을 복원하는 백업 파일은 아니다. 새 저장 키는 추가하지 않는다.

## 5. 확인 결과와 한계

- 변경 JavaScript 구문 검사와 Git 공백 검사를 수행했다. 사용자 요청 없이 자동 테스트를 추가하거나 실행하지 않았다. 이전 166개는 WEB-020 당시 기록이다.
- 별도 localhost 가상 기록으로 6→7 이동, 초안 저장, 접기·펼치기, 기본 PDF 선택, Word 선택, 생성 중 비활성, 완료 안내를 확인했다. 사용자 127.0.0.1 저장 자료는 변경하지 않았다.
- 실제 브라우저에서 PDF와 DOCX를 내려받았다. DOCX는 ZIP/OOXML 본문·지표 표·한글·숫자·내장 글꼴을 읽어 확인했다.
- PDF 렌더에서 KR 글꼴의 아래첨자 누락을 발견해 라틴 글꼴을 함께 사용하는 방식으로 수정했다. 수정 후 브라우저 PDF의 kgCO₂e 텍스트 보존을 확인했다.
- 마지막 여백/소제목 조정과 두 글꼴을 사용하는 최종 생성 모듈로 가상 PDF·DOCX 샘플을 별도로 생성했다. PDF 2쪽을 Poppler로 렌더하고 전 페이지를 열어 한글·아래첨자·수치·표·페이지 번호·잘림 여부를 확인했다. DOCX는 두 글꼴 포함·OOXML 표 3행과 원문을 확인했다.
- documents 스킬의 DOCX 렌더러를 시도했지만 이 Windows 번들에는 LibreOffice가 없어 실패했다. 사용자 설치본으로 대체하지 않았다. 따라서 Word·LibreOffice에서의 최종 시각적 줄바꿈·페이지 배치와 실제 열기는 미확인이다. OOXML 구조 확인을 시각적 렌더 확인으로 설명하지 않는다.
- 큰 데이터의 여러 페이지·최대 길이·모바일 전용 크기, 로드/생성 실패 주입과 생성 중 다른 탭 변경은 이번 실행에서 재현하지 않았다. 관련 보호는 구현·코드 검토 범위다.

화면 증거: `report-export-options.jpg`. 최종 PDF 렌더: `report-export/final-report-page-1.png`, `final-report-page-2.png` (대화의 시각화 출력 폴더). QA용 가상 문서와 이미지 자체는 GitHub에 올리지 않는다.

## 6. 쉬운 설명

“보고서를 내려받는 부분을 펼치고 PDF나 Word를 고른 다음 내려받기를 누릅니다. 저장된 내용으로 이 브라우저가 문서를 만듭니다. PDF는 읽기 편한 양식이고 Word는 내용을 편집할 수 있는 문서입니다. 실제 증빙 파일은 문서 안에 붙이지 않습니다.”
