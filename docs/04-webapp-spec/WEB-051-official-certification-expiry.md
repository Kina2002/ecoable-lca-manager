# WEB-051 인증서의 공식 만료일 기록

기준: 설계서 v02 F-12. WEB-049의 계산 날짜와 WEB-050의 갱신 안내가 실제 발급 문서의 유효일과 다를 수 있으므로, 확인한 날짜를 별도로 기록한다.

## 왜 만드는가

자동 계산은 달력으로 예측한 날짜다. 인증서나 등록 기록에 실제로 적힌 날짜가 다르면 사람이 확인한 날짜로 업무 일정을 잡아야 한다. 특히 프로젝트가 완료된 뒤에도 유효기간 관리는 계속된다.

## 입력과 규칙

- 승인·등록 상태인 **인증 또는 등록**의 공식 만료일, 확인 문서 이름, 확인 담당자, 확인 근거·정정 사유를 기록한다. 발급 문서와 등록 번호를 확인했다는 체크를 요구한다.
- 공식 만료일은 발급·등록일 이전일 수 없다. 고객 제출이나 미승인 기록에는 입력할 수 없다. 9단계와 완료·사후관리 10단계에서 입력한다.
- 같은 인증서의 날짜를 정정하면 새 이력을 남긴다. 발급일·제도·인증 번호가 바뀌면 이전 확인 이력을 보존하되 새 기록의 날짜로 사용하지 않는다.
- 문서 날짜가 있으면 그 날짜를 WEB-050 갱신 안내의 기준으로 쓰고, 아직 없으면 WEB-049 예상일을 쓴다. 계산 규칙이 없는 다른 제도도 문서 날짜가 있다면 이를 기준으로 6개월 전 안내한다. 화면과 할 일에서 **문서에서 확인한 날짜/예상일**을 구별한다.
- 문서 파일 자체는 업로드하지 않는다. 이름과 확인 근거를 기록한다. 기관의 최신 등록 상태는 사람이 다시 확인해야 한다.

## 저장과 보호

기존 `certification.v1`에 `validity` 이력 이벤트를 추가한다. 기존 기록은 그대로 읽으며, 백업·복원과 프로젝트 삭제는 기존 인증 기록 키를 사용한다. 완료 이벤트 뒤에도 만료일 확인 이벤트만 허용한다. 저장 시 기록 수정 차수를 다시 확인해 오래된 화면이 최신 날짜를 덮지 않도록 한다. 잘못된 저장 기록은 읽기 실패로 처리하고 원문을 보존한다.

## 검증

완료 프로젝트의 문서 날짜 저장·복원·갱신 할 일 기준 변경, 계산 규칙이 없는 제도의 문서 날짜 적용, 발급일 이전 날짜·문서 누락·오래된 화면·손상 이력 거절을 검사했다. 전체 자동검사 **239개**, 변경 JavaScript 구문, 정적 자산 HTTP 200, Git 공백 검사가 통과했다. 실제 브라우저의 입력·좁은 화면 조작은 별도 확인이 필요하다.

면접 설명: “처음에는 발급일에서 만료일을 예상하지만, 실제 인증서 날짜가 다를 수 있습니다. 그래서 담당자가 확인 문서와 실제 만료일을 기록하면 그 날짜가 갱신 할 일에 우선 적용되도록 했습니다. 누가 왜 정정했는지도 이력으로 남습니다.”
