# WEB-003 프로젝트 상세 보기

- 기준: [설계서 v02](../02-design/lca-webapp-design.md) 5-2장 Project, 7-1장 프로젝트 상세, 9-3장 샘플.
- 범위: F-01의 프로젝트 한 건 조회와 개요·범위 설명 부분.
- 합의: 프로젝트 번호로 상세 열기, 목적·동인·활용처와 기준량·경계 설명, 목록 복귀 시 단계 필터 유지.
- 상태: 구현·브라우저 검증 완료. 코드와 이 문서를 같은 커밋으로 관리한다.

## 1. 왜 만드는가

목록은 여러 프로젝트를 비교하는 목차다. 한 줄에 모든 설명을 넣으면 읽기 어렵다.
상세는 목차에서 고른 업무의 설명서다. 누가 어떤 제품을, 왜, 어디까지 평가하는지 한 건씩 읽는다.
이 화면은 이후 데이터 요청·검토 등의 업무를 특정 프로젝트와 연결할 때 사용할 바탕이 된다.
이번에는 조회만 구현한다.

## 2. 사용 흐름

1. 전체 목록 또는 단계로 거른 목록에서 프로젝트 번호를 누른다.
2. 해당 회사 이름과 '가상' 표시가 있는 상세 화면이 열린다.
3. 업종·프로젝트 유형·현재 단계·목표 완료일을 읽는다.
4. 업무 목적·세부 동인·결과 활용처를 구분해 읽는다.
5. 대상 제품·기준량·시스템 경계와 해당하는 평가 모듈을 읽는다.
6. '목록으로' 또는 주 메뉴의 '프로젝트'를 누른다.
7. 원래 단계 필터와 목록이 그대로 보이며, 눌렀던 프로젝트 번호에 키보드 초점이 돌아간다. 목록의 스크롤 위치도 복원한다.

예: '데이터 검토 1개' → 'LCA-2026-003' → 다온케미칼 상세 → '목록으로' → 데이터 검토 목록 1개.

## 3. 표시 정보와 쉬운 뜻

| 화면 정보 | 데이터 필드 | 뜻 |
|---|---|---|
| 고객사와 가상 표시 | `companyName`, `isFictional` | 실제 고객 기록과 혼동하지 않도록 회사명 옆에 '가상' 표시 |
| 제품·프로젝트 번호 | `productName`, `code` | 어떤 제품의 어떤 업무인지 구분 |
| 업종·프로젝트 유형 | `industry`, `type` | 산업 분야와 맡은 업무의 종류 |
| 현재 단계 | `stage` | 공통 10단계 중 현재 속한 단계. 단계 번호는 완료율이 아님 |
| 목표 완료일 | `targetDate` | 기존 샘플 명단과 같은 시연용 일정. 앱을 연 날짜를 기준으로 생성 |
| 업무 목적 | `purpose` | 왜 일을 하는지 |
| 세부 동인 | `drivers` | 관련된 구체적인 요구·기준. 규제 적용 여부를 자동 판정한 결과는 아님 |
| 결과 활용처 | `uses` | 결과를 어디에 쓰려는지. 인증을 이미 취득했다는 뜻은 아님 |
| 평가 기준량 | `functionalUnit.qty`, `.unit` | 결과를 제품 얼마만큼당으로 정리할지. 실제 생산량과 다름 |
| 시스템 경계 | `boundary` | 제품의 시작부터 어느 과정까지 살펴볼지 |
| 평가 모듈 | `modules` | 값이 있는 프로젝트에만 표시. 샘플은 솔뫼철강의 A1–A3 |

목록에서 사용하던 7개 프로젝트를 그대로 읽는다. 상세용으로 별도의 프로젝트 명단을 복사하거나 새 목표일을 만들지 않는다.
고객 담당자·담당 연구원·기준기간처럼 아직 샘플에 없는 정보를 지어내지 않는다.

### 목적·동인·활용처의 차이

- 목적: '왜 하나요?' — 고객사의 요구에 대응하기 위해서.
- 동인: '어떤 요구인가요?' — 프로젝트에 기록한 Catena-X·EU 배터리법 등.
- 활용처: '결과를 어디에 쓰나요?' — PCF 정보나 환경성적표지 준비 등.

목적은 큰 이유, 동인은 구체적인 배경, 활용처는 목표로 하는 쓰임이다.
이 샘플은 가상 시나리오다. 특정 규제가 실제 회사에 적용된다거나 인증을 취득했다고 주장하지 않는다.

### '1 t · 요람~문 (A1–A3)'의 뜻

- 1 t는 1톤, 즉 1,000 kg이다. 결과를 제품 1톤 기준으로 정리한다는 뜻이다.
- 요람~문은 원료 확보·운송·제조부터 공장 출하까지다. 출하 후 사용·최종 폐기는 제외한다.
- A1은 원료 공급, A2는 원료 운송, A3는 제품 제조를 가리키는 건설제품 평가 단계 표기다.
- 요람~무덤은 유통·사용·수명 종료 후 폐기나 재활용 처리까지 포함한다.
- '패널 1장'처럼 수량만으로는 다른 제품과 공정하게 비교하기 어렵다. 실제 비교에는 기능·성능·수명 등 조건도 정해야 한다.

위 설명은 [WEB-001의 용어 설명과 참고 출처](WEB-001-project-list.md#10-함께-읽는-화면-용어)를 화면에 옮긴 것이다.
앱이 환경영향이나 탄소배출량을 계산하는 것은 아니다.

## 4. 동작 규칙

- 프로젝트 번호는 실제 동작하는 버튼이다. 접근성 이름에 번호·회사명·'상세 보기'를 포함한다.
- 프로젝트 조회에는 고유한 `id`를 사용한다. 필터 후의 행 순서나 회사명으로 찾지 않는다.
- 목록과 상세는 같은 HTML 안의 두 영역이다. 상세를 열면 목록 영역을 `hidden`으로 숨기고, 목록으로 돌아오면 다시 펼친다.
- 상세 제목에 키보드 초점을 옮겨 바뀐 화면을 읽을 수 있도록 한다. 브라우저 탭 제목과 상단 위치 표시도 갱신한다.
- 원래 목록을 다시 그리지 않으므로 선택한 단계·건수·목록이 유지된다. 돌아올 때 원래 버튼과 스크롤 위치도 복원한다.
- 상세 내용은 매번 새로 그린다. 다른 프로젝트의 활용처나 평가 모듈이 남지 않는다.
- Enter·Space로 버튼을 사용할 수 있다. 목록의 프로젝트 번호는 밑줄과 화살표로 누를 수 있음을 표시한다.
- 데이터는 `textContent`와 DOM 생성으로 표시한다. 데이터 문장을 HTML로 해석하는 `innerHTML`은 사용하지 않는다.
- 현재 단계나 목표일을 찾지 못하면 각각 '단계 확인 필요', '미정'으로 표시한다. 비어 있는 동인·활용처도 '미정'으로 표시한다.
- 상세의 현재 단계는 기존 공통 단계 이름만 읽는다. 아직 v02로 완성하지 않은 인증·단계 이동 규칙은 실행하지 않는다.
- PC·태블릿은 설명 카드를 두 열, 760px 이하에서는 한 열로 표시한다.
- URL이나 브라우저 방문 기록을 추가하지 않는다. 상세 복귀는 화면의 '목록으로'나 주 메뉴를 사용한다.
- 새로고침하면 전체 프로젝트 목록 7개에서 다시 시작한다. 상세 선택·필터를 저장하거나 상세 주소로 직접 접근하는 기능은 포함하지 않는다.

## 5. 파일과 데이터 흐름

| 파일 | 역할 |
|---|---|
| `web/index.html` | 목록·상세 영역, 목록 복귀 버튼, 새 화면 스크립트 연결 |
| `web/css/app.css` | 프로젝트 번호 버튼, 상세 정보와 설명 카드, 반응형 배치 |
| `web/js/views/project-list.js` | 각 프로젝트 번호에 고유 ID를 담은 버튼 생성 |
| `web/js/views/project-detail.js` | 전달받은 프로젝트 한 건으로 개요·범위·용어 설명 표시 |
| `web/js/app.js` | 고유 ID로 프로젝트 찾기, 화면 전환, 초점·스크롤 복원 |

동작 순서:

1. `data.js`가 앱을 열 때 샘플 7개를 만든다. 기존 동작이다.
2. `project-list.js`가 프로젝트 번호 버튼에 `data-open-project="project-003"`처럼 ID를 붙인다.
3. `app.js`가 클릭을 받아 `projects.find()`로 같은 ID의 프로젝트를 찾는다.
4. `projectDetail.render(project)`가 상세 내용을 만든다.
5. 목록을 숨기고 상세를 보여준다. 원본 프로젝트 값과 `selectedStage`는 바꾸지 않는다.
6. 복귀할 때 상세를 숨기고 이전 목록을 펼친다.

ID는 설명서의 관리 번호, 화면의 줄 번호는 설명서가 꽂힌 위치에 해당한다.
설명서를 거르거나 순서를 바꿔도 관리 번호로 찾으면 같은 업무를 열 수 있다.

변경한 CSS·JS 주소의 버전은 `?v=web-003`으로 갱신했다. 수정하지 않은 기존 파일은 버전을 유지한다.
브라우저가 수정 전 파일을 캐시에서 재사용하는 혼선을 줄이기 위해서다.

## 7. 면접 설명

**왜 상세 화면을 만들었나요?**

목록은 여러 업무를 빠르게 비교하기 위한 화면이라 긴 설명을 모두 넣기 어렵습니다.
상세에서는 선택한 업무의 목적과 평가 범위를 한 건씩 이해할 수 있게 했습니다.

**목록과 상세의 정보가 다르게 표시되는 문제를 어떻게 피했나요?**

동일한 프로젝트 객체를 읽습니다. 별도의 상세용 샘플을 만들지 않고 고유 ID로 원본 명단에서 찾습니다.

**필터를 해도 다른 프로젝트가 잘못 열리지 않는 이유는 무엇인가요?**

첫째 줄·둘째 줄 같은 화면 위치 대신 바뀌지 않는 프로젝트 ID를 사용하기 때문입니다.

**목록으로 돌아와도 필터가 남는 이유는 무엇인가요?**

목록과 선택한 단계는 그대로 두고 목록 영역만 잠시 숨깁니다. 복귀하면 같은 영역을 펼칩니다.
사용자가 보던 프로젝트를 계속 찾기 쉽게 초점과 스크롤 위치도 복원합니다.

**왜 인증 활용처와 인증 상태를 구분하나요?**

'환경성적표지에 쓰겠다'는 계획과 '환경성적표지를 취득했다'는 사실은 다릅니다.
이번 화면은 활용 계획만 보여줍니다. 실제 번호·유효기간·상태는 별도의 인증 관리 기능에서 다룰 예정입니다.

## 8. 이번 기능의 경계

등록·수정·삭제·단계 변경, 프로젝트 저장, 담당자·연구원 정보 추가, 데이터 요청·검토·메일·인증 관리, 공개 데이터 적용은 포함하지 않는다.
설계서의 프로젝트 상세 전체(10단계 막대·단계 안내·업무 탭)를 완성했다고 표시하지 않는다.
현재는 개요·범위 조회 부분이며, 나머지는 각각 범위를 합의한 뒤 구현한다.
다음 기능은 사용자가 이 화면과 설명을 확인한 뒤 함께 정한다.
