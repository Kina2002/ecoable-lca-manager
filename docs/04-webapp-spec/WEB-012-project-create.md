# WEB-012 새 프로젝트 등록

## 1. 왜 만드는가

샘플 7개를 조회하는 것에서 나아가, 새로 맡은 업무를 직접 등록하도록 만든다. 프로젝트는 ‘이 회사의 이 제품에 대해 이런 목적의 일을 한다’는 업무의 이름표다. 평가 범위를 결정하거나 실제 자료를 받는 것과는 별개다.

설계서 v02 **F-01 생성 기능의 첫 부분**, F-10 브라우저 저장의 확장이다. 전체 프로젝트 관리나 전체 단계 이동을 완성한 것은 아니다.

## 2. 합의 범위와 입력

사용자가 ‘새 프로젝트 등록 기능 만들어보자’고 승인했다. 입력은 네 가지로 제한한다.

| 항목 | 규칙 | 쉬운 의미 |
|---|---|---|
| 회사명 | 필수, 앞뒤 공백 정리, 최대 100자 | 누구의 업무인가 |
| 제품명 | 필수, 앞뒤 공백 정리, 최대 100자 | 어떤 제품을 평가하는가 |
| 업무 목적 | 필수, 고객사 요구 대응 / 규제 대응 / 제품 환경성 진단 | 왜 이 일을 하는가 |
| 목표 완료일 | 필수, 실제 달력 날짜 | 언제까지 마치려는가 |

목표일은 숫자 8자리 입력·연도 4자리·달력을 기존 날짜 입력과 같이 사용한다. 과거 날짜도 이력·시연 입력을 위해 허용한다. 미래 여부로 업무 적합성을 판정하지 않는다.

지금은 가상 데이터 시연 단계이므로 새로 등록한 회사도 **가상**으로 표시한다. 모달 제목과 안내에 이를 표시하며 실제 고객 기록으로 설명하지 않는다.

## 3. 사용 흐름

1. 프로젝트 목록 상단 ‘새 프로젝트 등록’을 누른다.
2. 모달에서 네 항목을 입력하고 프로젝트 등록을 누른다.
3. 저장 성공 후 모달을 닫고 계약·착수 단계 필터로 전환한다. 새 번호 버튼에 초점을 옮기고 해당 위치가 보이도록 스크롤한다.
4. 전체 건수와 계약 단계 건수가 증가한다. 새 프로젝트 번호를 눌러 상세를 본다.
5. 새로고침해도 같은 ID·번호·입력 목표일과 기본 정보가 유지된다.

다른 단계 필터를 보다가 등록해도 새 프로젝트가 숨지 않도록 계약 단계 목록을 보여준다. 기존 상세 화면에서만 범위 상태를 눌러 범위 기록으로 바로 이동하는 정책을 유지한다.

취소·Escape는 등록하지 않고 창을 닫는다. 다음에 열면 새 입력을 시작한다. 오류 발생 시 창과 입력값을 유지하고 첫 오류 입력칸에 초점을 옮긴다. 저장 실패 후 다시 제출할 수 있다. 성공 후 닫기 이벤트에서 목록을 갱신해 초점이 등록 버튼으로 덮어씌워지지 않도록 한다.

## 4. 새 프로젝트의 시작 상태

- 프로젝트 전체 단계: **계약·착수(1)**.
- 범위 합의 상태: **미정**.
- 기준량·단위·경계·기준기간·적용 기준·협의 메모: 비어 있음.
- 업종·프로젝트 유형·세부 동인·결과 활용처는 이번 등록 화면에서 입력받지 않고 미정으로 표시한다.
- 목표일 설명은 샘플의 상대 일정 설명 대신 ‘등록 때 직접 입력한 목표일’로 표시한다.
- 자료 요청은 자동 생성하지 않는다. 기존 요청 탭·범위 초안 기록은 새 프로젝트에도 연결한다.
- **계약→범위 단계 이동은 아직 별도 후속 기능**이다. 범위 확정을 저장해도 계약에서 수집으로 건너뛸 수 없다. 이번 작업에 임의로 추가하지 않는다.
- 프로젝트 기본정보 수정·삭제·검색·연락 담당자 입력·일괄 요청 생성·내보내기·서버 DB·AI·공개 배포는 추가하지 않는다.

## 5. 식별과 저장

- 키: `ecoable-lca-manager.projects.v1`, 형태 `{version:1,nextNumber,projects:[직접 등록한 기본 기록]}`.
- 기본 샘플 7개는 기존 `data.js`에 둔다. 등록 저장소에는 직접 등록한 기본 정보만 추가한다.
- 첫 등록 번호는 기본 샘플의 최대 번호 다음인 8이다. 현재 기준 연도라면 `LCA-2026-008`이며, 이후 009, 010 순서다. 연도는 앱을 연 기준일을 사용한다.
- 내부 ID는 `project-user-8`처럼 샘플 ID와 구별하며 같은 ID를 범위·요청에 연결한다.
- 같은 회사·제품의 다른 계약도 있을 수 있으므로 회사·제품 이름만으로 중복을 막지 않는다. 번호와 ID로 업무를 구분한다.
- 다른 화면이 먼저 등록했으면 저장 직전에 최신 저장본을 다시 읽어 다음 번호를 사용한다. 동시에 발생하는 쓰기에 대한 원자적 잠금이나 다중 사용자 동기화는 제공하지 않는다.
- 저장이 성공한 뒤에만 새 프로젝트와 건수를 화면에 반영한다. 실패하면 번호도 소비하지 않는다.
- JSON 손상·다른 버전·중복 ID/번호·잘못된 필수 정보·카운터 이상은 실패로 처리한다. 원본을 지우거나 덮어쓰지 않는다.
- 최초 목록 읽기 실패 시 상단에 최신 저장 목록을 확인하지 못했음을 알리고 기본 샘플만 보여주며 등록 버튼을 비활성화한다. 복구 후 새로고침이 필요하다.

## 6. 기존 자료를 유지하는 연결

범위와 요청은 각각 기존 `scope.v1`, `requests.v1`을 그대로 쓴다. 등록 저장소를 먼저 읽어 전체 프로젝트 ID를 확보한 뒤 두 저장소를 연결한다.

등록 성공 후 기본 명단을 다시 연결하고, 저장된 범위를 읽어 기존 단계·메모를 복원한다. 요청 저장소도 전체 프로젝트 ID로 다시 연결한다. 수집 현황은 최신 요청 저장소와 현재 프로젝트 배열을 참조한다. 등록 과정에서 기존 범위·요청 키를 쓰거나 초기화하지 않는다.

다른 탭의 새 프로젝트가 현재 탭에 실시간 추가되는 기능은 없다. 새로고침하면 전체 명단을 다시 읽는다. 모르는 ID가 연결된 저장본은 기존 정책대로 오류를 내어 잘못된 덮어쓰기를 막는다.

## 7. 검증

- `node --test web/tests/*.test.cjs`: **86개 통과**. 기존 74개 + 프로젝트 등록 검사 12개.
- 샘플 조회 무쓰기·원본 보존, 입력 정리·초기 상태·번호, 새 저장소 복원, 같은 이름의 다른 업무·다른 저장 객체의 번호 연결, 필수·길이·목적·날짜 검사, 경계값·윤년·과거 날짜, 저장 실패 재시도, 손상 보존·접근 거절을 확인했다.
- 새 프로젝트에 범위·자료 요청을 연결하고 복원하는 통합 검사를 수행했다. 등록 전의 기존 범위 메모·받은 자료·검토 승인·수집 필터·단계 건수가 등록 후에도 유지되고 기존 두 저장소 원문이 바뀌지 않는지 확인했다.
- JavaScript 구문, HTML ID·레이블·ARIA·스크립트 경로 연결, HTTP 응답, 공백 오류를 확인한다.
- 이전 브라우저 접근이 보안 정책으로 차단되어 우회하지 않았다. **실제 모달 열기·입력·취소·Escape·달력·클릭·초점·스크롤·작은 화면은 미확인**이다. 사용자 화면 확인이 필요하며 자동 검사 통과로 UI 확인을 대신했다고 설명하지 않는다.

## 8. 사용자 확인 예시

회사 ‘푸른소재’, 제품 ‘재생 플라스틱 칩’, 목적 ‘고객사 요구 대응’, 목표일을 입력한다. 저장 후 계약 단계 건수가 하나 늘고, 새 번호로 상세가 열리는지 확인한다. 범위가 미정이고 기록을 입력할 수 있는지, 새로고침 후에도 프로젝트·목표일이 남는지 확인한다. 취소 시 건수가 늘지 않는지도 확인한다.

## 9. 파일과 면접 설명

- `projects.js`: 등록 기본정보 검사, ID·번호 생성, 저장·복원.
- `views/project-create.js`: 모달 입력·오류·날짜·취소·등록 후 연결.
- `app.js`: 명단과 범위·요청 저장소 연결, 계약 단계·건수 갱신.
- `views/collection.js`: 초기 명단에 고정하지 않고 현재 프로젝트를 조회한다.
- `views/project-detail.js`: 직접 입력한 목표일 설명.
- `projects.test.cjs`: 등록·보호·기존 데이터 연결 검사.

면접 설명 예: ‘샘플 조회에서 끝나지 않도록 새 업무 등록을 만들었습니다. 기본정보만 입력받아 계약 단계와 범위 미정으로 시작하고, 합의가 필요한 범위는 나중에 기록하게 했습니다. 같은 회사의 여러 의뢰를 구별하도록 고유 번호를 붙였고, 등록 저장소를 기존 범위·자료 기록과 분리해 기존 데이터를 유지했습니다.’
